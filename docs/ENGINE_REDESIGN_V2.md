### 1.2 算力的账（回答「能不能再优化」）

本机（`nproc` 12，6 物理核；压测报告口径）指令吞吐按 9.66 GIr/s 计（轮次135 起沿用）。

| 项 | 实测 | 需要（1M nps） | 因子 |
| --- | --- | --- | --- |
| Ir/节点 | 42,353.5 | ≤ 9,660 | 4.4 |
| Ir/候选格 | 942.4 | ≤ 215 | 4.4 |
| ns/节点（折算） | 4,385 ns | ≤ 1,000 ns | 4.4 |

成本形状（轮次141 callgrind，一把定深 4、预算 8000 的预搜，7,881 节点，I refs 571,718,793）：

| 函数 | Ir 占比 | 性质 |
| --- | --- | --- |
| `Evaluator::pattern_score` | 20.85 % | 每颗已占子逐子聚合 |
| `PatternRecognizer::finish_direction` | 14.45 % | **读棋盘的逐格走线**（`pattern.cpp:363-487`：`run_length` / `fill_run` / `painted` 三段 lambda） |
| `CandidateCache::cell` | 8.20 % | 已是线字键缓存 |
| `recognize_position_both` | 8.18 % | 双色单次扫描 |
| `match_pattern` | 7.58 % | 已是 2^18 查表 |
| `fill_pattern_lut` | 5.64 % | **一次性**建表，不是稳态成本 |

三个结论，是 §2 全部设计的前提：

1. **稳态成本集中在评估族**：轮次136 量到评估族占节点成本 69.19 %。因此「把评估族做到 0」也只有 3.23 倍上限——这是算术，不是工程态度问题。
2. **`finish_direction` 不是纯查表函数**：它一半的成本花在「窗口给了形状，但形状能不能变成威胁只有棋盘知道」的黑棋特判上（黑棋长连禁手、活四是否真活、活三是否真活）。所以它**不可能**简单并进现有 2^18 窗口 LUT——这条必须写清楚，否则会重犯 v1.0 之前那次被否决的「全盘增量评估」式乐观（README 已记录那次否决）。
3. **节点数里最大的一块不是「评估」，是「静默」**：轮次137 量到一次 d6 思考 **64.5 %** 的节点是静默（quiescence）节点。所以任何只盯 `alphabeta` 主干的内核优化，天花板都在剩下那 35.5 % 里。

## 2. 问题一：算力——CPU 三改 ＋ 一入库，GPU 放对位置

### 2.1 先把 GPU 的物理账算清（结论：不进单次思考）

| 量 | 级 | 说明 |
| --- | --- | --- |
| 一个节点的 CPU 成本 | 4,385 ns | 42,353.5 Ir ÷ 9.66 GIr/s |
| `Board` 副本 | 0.118 µs（`sizeof(Board)` = 4,664 B） | 轮次141 实测 |
| 线程起 + join | 28.92 µs | 轮次141 实测（≈ 6.6 个节点的钱） |
| GPU kernel 启动 + 一次往返 | 5–20 µs 量级 | **未实测**（本机为 AMD RX 6600 XT，WSL 下无 ROCm，原生 Linux 需 Vulkan 路径，见下方更正块），量级估算 |
| 每节点候选格评估次数 | 44.94 次 | 42,353.5 ÷ 942.4（实测比值） |

三条不可逾越的理由：

1. **搜索是延迟型负载，不是吞吐型负载。** 一次思考是深度优先的单链：下一层搜什么取决于上一层剪枝结果；GPU 拿到棋盘时 CPU 已经无事可做。把候选评估搬上 GPU，等于给每个节点加 5–20 µs 去买一个本地 0.94 µs 就能做完的事。
2. **批处理数量不够。** 每个节点只有约 44.94 次候选格评估，一次 d6 思考同时存在的「可并行前沿」≈ 各层在搜的候选数之和，撑不满一个 GPU 的占用率。GPU 要吃饱需要成百上千个**互相独立**的局面——这只有自我训练、并发会话和 §6 的复盘批处理能给。
3. **热点函数已经是查表形态。** `pattern_score` / `match_pattern` / `finish_direction` 的稳态热点都是 L1/L2 命中的小表读；搬上 GPU 的成本先花在「把 4,664 B 的棋盘搬过去」。

> **本机状态（2026-10-21 更正，此前两次自检的结论是错的）**
>
> 轮次142 与本版初稿都写过「本机无 GPU」，依据是 `nvidia-smi` 不存在、`/dev/dri` 不存在。**那两次探测是在 Windows 侧的 Git Bash（MINGW64）里跑的，而该 shell 根本不可能有 `/dev/dri`——Linux 设备节点只存在于 Linux 里。** 更正后的实测：
>
> | 项 | 实测 | 含义 |
> | --- | --- | --- |
> | Windows 侧显卡 | **AMD Radeon RX 6600 XT**（Navi 23 / gfx1032，RDNA2），驱动 32.0.21045.5002 | 硬件与 Windows 驱动都正常，**不是「没识别到」** |
> | 宿主 CPU / 内存口径 | i5-10500，6 物理核 / 12 逻辑核 | 与既有读数一致 |
> | WSL 功能 | `Microsoft-Windows-Subsystem-Linux` 与 `VirtualMachinePlatform` 均 Enabled | WSL2 可用（`wsl.exe` 被本会话沙箱拦，未能进 WSL 内自检） |
> | `nvidia-smi` | 不存在 | 对 AMD 卡本来就不存在，**不构成「无 GPU」的证据** |
>
> 三条结论，直接改写了本节的边界：
>
> 1. **WSL 下 AMD 显卡只会以 `/dev/dxg` 出现，不会出现 `/dev/dri`。** 那是 WSL 的半虚拟化 D3D12 路径（WSLg），没有 `amdgpu` 内核模块，因此 `rocm-smi` / `clinfo` / `/dev/dri/renderD128` 一律查不到——**这是 WSL 的正常形状，不是驱动坏了**。
> 2. **AMD 在 WSL 下没有 ROCm/HIP。** 所以「把 `BatchEvaluator` 写成 HIP 内核」在 WSL 里连编译目标都不存在。
> 3. **原生 Linux 下 gfx1032 不在 ROCm 官方支持列表**（官方覆盖 gfx1030 的 6800/6900 与 gfx1100 的 7900 系列），要走 `HSA_OVERRIDE_GFX_VERSION=10.3.0` 这种未支持路径；而 **Vulkan 计算（Mesa RADV）对 gfx1032 是完整支持的**。
>
> **所以本版把 O6 的后端从「CUDA 或 HIP」改成「Vulkan compute（首选，RADV 原生 / Dozen 于 WSL）＋ HIP（仅原生 Linux，且为未支持路径）」。** 运行时探测的三级降级是：`vulkaninfo` 有设备 → Vulkan；否则 `rocm-smi` 有设备 → HIP；否则 CPU。**单次思考不进 GPU 的结论不变**（§2.1 三条理由是延迟与批量的算术，与厂商无关），但「本机无 GPU」这句话不再成立，O6 的盈亏平衡点必须**在真机上重测**，不能用「本机没有」当免测理由。

### 2.2 CPU 内核三改 ＋ 一砍

下面每项按本仓库的规矩写：**现状读数 → 改什么 → 差分测试 → 预期（未测）→ 杀线**。预期省幅全部是预估；任何一项在刺探里做不到预期，走杀线，不落半截。

#### O1｜`finish_direction` 升格为「线段局部 LUT」

**现状**：占 14.45 % Ir，做的是棋盘走线。但它读的内容是有界的：

- 黑棋特判的三个分支（`pattern.cpp:417` LIVE_FOUR/RUSH_FOUR 的 `five_points`、`:446` LIVE_THREE 的 `live`、`:383` FIVE 的 `run_length() >= 6`）只沿 `dir` 一条线、以 `(row, col)` 为中心 ±6 格内做判断；
- 输入是这条线上 13 个格子的三态串（EMPTY / BLACK / WHITE）＋ 一个由中央 9 格窗口给出的基础 `PatternType`，而基础类型**已经**是现有 2^18 窗口 LUT 的输出；
- 输出只是「修正后的 `PatternType`」，白棋分支的 `LONG_FIVE → FIVE` 降级也是纯函数。

**改什么**：把「13 格三态 → 修正后类型」做成第二张表。

- 索引 3^13 = 1,594,323 项（≈ 1.6 MB），`uint8` 打包「基础类型 3 位 ｜ 黑棋修正类型 3 位」；建表时用现有 `finish_direction` 的纯函数副本跑满一次，**不新写判断逻辑**（避免第二份语义漂移）；
- 查询：从 `board.lines_[color][dir][line]`（`board.h:108`）shift + mask 取出 13 格（约 10 条指令）＋ 一次表读。

**差分测试（照 v1.0 `:556` 的形状）**：42 支普查棋盘 × 225 格 × 4 方向 × 2 色 = 75,600 组，逐组比 LUT 值与现函数值；同一棋盘集上再逐格比 `recognize_position_both` 的聚合字段，确认误差没有从另一条路径渗回来。

**预期**：该函数稳态成本降 80–90 %，约省整节点成本的 11–13 %。**未测。**

**杀线**：刺探若发现线字取窗的指令数超过估值两倍（即省下的只是函数调用开销），或 75,600 组里有 1 组不一致 → 本项作废，不落树。

#### O2｜已占子的线字键缓存（`StoneCache`，打 `pattern_score` 那一半）

**现状**：`pattern_score` 占 20.85 %，在 `evaluate_board` 里对每颗已占子调用（`evaluator.cpp:245-248`），一子四方向全重算。`CandidateCache`（`search_state.h:226`）已经用「四 uint64 线字键」把**候选空格**的分数缓存做成「条目自带过期判据」的形状（轮次137），这是本树既有先例。

**改什么**：同一形状搬到已占子上。

- 每个已占格一份记录：四方向线字键 ＋ `PositionPattern` ＋ `pattern_score` 贡献；
- 一次 `evaluate_board` 逐子查键：键不变 → 用旧贡献；键变 → 重算并更新；
- 一手棋只改经过落子的 4 条线，所以每手需重算的已占子约 20–48 颗，其余约 180 颗是键比对命中。

**差分测试**：沿用 O1 的 42 棋盘集，另加「同一棋盘连落 N 手、每手比对 `evaluate_board`」的时序形状（键缓存最容易在时序上错，不在横截面上错）。

**预期**：评估族稳态成本降 40–60 %，约省整节点成本 12–18 %。**未测。**

**杀线**：键比对本身是 4 × uint64 × 225 子 ≈ 900 条指令/次；若「命中省的钱不比键贵多少」，本项作废。**刺探只产出一个数：Ir/已占子。**

#### O3｜排序分与威胁分分离

**现状**：`CandidateCache::cell` 8.20 % ＋ `recognize_position_both` 8.18 % 是排序路径的成本，而排序真正需要的只是「谁是冲四/活三/挡点」，不需要两色全量 `candidate_pair_value`（那是叶子的活）。

**改什么**：排序路径改用「行棋方四条线的成五/成四/活三判定」，四线位窗口已在 `board.lines_` 里，做成 O(1) 线字判定；两色全量配对分只保留在叶子（`stand_pat`、`evaluate_board`）。

**预期**：排序路径降 50 % 以上，约省整节点成本 6–8 %。**未测。**

**杀线**：以「Ir/候选格」单一读数决生死；同时必须用 §1.1 的固定针臂确认着法与分值不变（排序路径改动的代价是可复现选点，本仓库已有三次「机制建好后判不落地」的先例）。

#### O4｜一砍：只读表预算重新记账

`fill_pattern_lut` 在预搜臂里占 5.64 % Ir（32.2 M Ir 一次性）；O1 会再加一张 1.6 MB 表。**砍的是重复建表**：建表必须进程内一次，可选落盘缓存；O1 落树后，建表成本单独记进启动开销，不许藏在吞吐数字里。

### 2.3 O5｜战术层证明入库：现在「证明过的杀」只活在一次思考里

**现状（实测，§1.4 最后一行）**：`VCFSearch` 与 `VCTSearch` 各自只把 `TranspositionTable&` 绑在成员上，`vcf.cpp` / `vct.cpp` 里**没有任何一次 probe/store**。于是同一次思考里：

1. VCF 用 20 % 预算证明了「这条路能杀」，返回 `method="vcf"`，思考结束；
2. 若 VCF 只证明了「有杀但没走通」（`UNKNOWN`），AlphaBeta 接着从同一个根往下搜，**把同一棵强制树又爬一遍**；
3. 下一手（同一会话、同一张表）里，对手按 VCF 主变应了一手，主搜索对那个已经证明过的局面**一无所知**。

这不是「少一个优化」，是**同一份证明被买了三次**。轮次141 的 ponder 已经证明「同一笔 CPU 从人等的那一刻挪到等人落子的那一刻」是赚的（省下 ÷ 花掉 = 1.129 @ 50 % 预算），而这里连「挪」都不需要——证明已经算出来了，只是没有写下来。

**改什么**：

- 新增 `src/search/proof_table.h`：`ProofTable` 按 Zobrist 键存三元组 `{verdict: WIN_FOR(color) / LOSS_FOR(color) / UNKNOWN, distance_to_mate, best_move}`，容量 2^16 项 × 24 B ≈ 1.5 MB（与一张 worker TT 同量级，实测 7.3 MB/worker 的 1/5）；
- **写点只有两个**：`VCFSearch::search_impl` 返回 `WIN` 时写 `WIN`（带 `variation.size()` 作距离）；`find_defense` 返回 `PROVEN_LOSS` 时写 `LOSS`。`UNKNOWN` **一律不写**——「没证明」不是信息，写进去就是把未证明当证明用；
- **读点只有两个**：`VCFSearch::vcf_attack` 进节点先查（命中 `WIN` 直接返回 `100000 + dist`，命中 `LOSS` 直接返回 `-100000 + dist`）；`AlphaBetaSearch` 在 `alphabeta()` 的 TT 探测之后、候选生成之前查一次（命中就整节点短路，`method` 记 `proof`）；
- **代龄按手推进**，与 A3 给 TT 定的规则同一口径（一次思考 = 一代），`new_search()` 不老化它；
- **只对「杀」入库**：`|score| >= 90000` 的 VCT 胜也入（VCT 的 90000 是「活三杀」，与 VCF 的 100000 不是同一件事，距离字段照抄 `variation.size()`）。

**为什么这一条比 O1/O2/O3 便宜**：它不改任何一行评估，不碰 `pattern_score`，也不动排序；差分测试的对象是「**加表前后的着法与分值必须逐个相同**」——因为证明表只回答已经被证明过的局面，命中与不命中是同一件事的两种算法。

**预期**：省多少完全取决于「证明过的局面被重算几次」，本机**没有这个读数**，所以先刺探，刺探只出一个数：**同一把 d6 思考里，`alphabeta` 命中 `ProofTable` 的节点占比**。

**杀线**：

1. 命中占比 < 3 % → 本项作废（表 1.5 MB 换不到可测的节点数）；
2. 命中占比达标但节点数下降 < 2 % → 也作废：说明命中的节点本来就在 TT 或杀手着法下第一个剪掉，证明表只是把便宜的节点变便宜；
3. 任何一臂出现着法或分值变化 → 立即回滚（证明表的语义是「同一个答案换一条路径」，出现新答案就是 bug，不是收益）。

### 2.4 波前扩展（wavefront / BFS-by-level）：用户的方案，哪一半成立

用户的原话是「某些小逻辑重复性场景（如 VCF）可改成 GPU 异步加速，如波前扩展」。这句话里有两个独立的断言，必须分开判：

- **断言 A：VCF 是「小逻辑重复性场景」** → 部分成立。VCF 的每一层确实只做一件事（找冲四 → 找唯一挡点 → 再找冲四），逻辑小且重复；
- **断言 B：把它改成波前扩展（按层同步推进）就能上 GPU** → **在单次思考里不成立**，在批处理里成立。

#### 2.4.1 为什么单根内的波前是负收益

VCF 的树形不是宽树，是**窄而深的强制链**：每一层的冲四点通常只有 1–3 个，而对手的应手在绝大多数分支上是**唯一挡点**（`find_block_move` 就是靠这一点工作的）。于是：

| 量 | 单根 VCF 的实测/结构值 | 后果 |
| --- | --- | --- |
| 每层宽度 | 1–3（冲四候选），对手应手多为 1 | 波前一层只有 1–3 个任务，GPU 占用率 ≈ 0 |
| 层间依赖 | 严格：第 k+1 层的棋盘只能由第 k 层的落子产生 | 无法流水，只能同步；GPU 每层等一次往返 |
| 每层工作量 | 一次 `recognize_position_both` × 候选数 ≈ 6.78 µs（探针实测） | 一层的工作量 ≈ 1.5 个 CPU 节点的钱，小于一次 kernel 往返 |
| 提前退出 | VCF 找到第一条胜线就返回（`search_impl` 的循环） | 波前必须跑完整层才知道有没有胜线，**丢掉早退** |

把四行合起来：一次单根 VCF 是「几十个 6.78 µs 的串行小步」，波前化以后变成「几十次 GPU 往返的串行小步」，**每一步都更贵**。这不是工程实现问题，是树形问题。

#### 2.4.2 成立的形状：跨根波前（batch across roots）

波前扩展真正对得上的场景是「**同一层上有成百上千个互不依赖的根**」。本树里有四个这样的位置，全部已存在或已规划：

| 场景 | 根的来源 | 根数量级 | 现状 |
| --- | --- | --- | --- |
| 单节点内全候选战术筛查 | 一个节点的 44.94 个候选，每个都问「这里有没有 VCF」 | 45 / 节点 | 现在只做一次 `threat_probe`（O(候选) 布尔），**不做逐候选 VCF** |
| 复盘批处理（§6） | 一局 60 手 × 每手一个局面 | 60 / 局，10^4 / 千局 | 尚不存在 |
| 训练数据采集 | 每轮 `data_games` 局的每个 ply | 10^2–10^3 / 轮 | 已存在（`data_collector`），串行 |
| 开局筛选（§3.2 S2） | 每条候选开局的每个分支 | 10^3 | 尚不存在 |

**所以本版对波前扩展的裁决是**：

1. **CPU 侧的跨根波前：做。** 新增 `WavefrontBatch`（§6.2 的 B 段与 §3.2 S2 共用）：输入 `vector<(Board, color, budget)>`，输出每个根的 `{verdict, best_move, nodes}`；内部按层推进，**同一层的所有根一起算**，共享一张已预热的 LUT 与一份 `CandidateCache`。它不需要 GPU，本身就是 CPU 侧的收益（LUT 预热、分支预测、cache 复用），而且形状与「一次几千个局面」的复盘天然对齐。
2. **GPU 侧的跨根波前：留接口，不进树。** 接口 `BatchEvaluator::price(vector<PriceKey>, vector<PriceOut>)`（原 v2.0 的 O5，本版改编号为 **O6**），入参只用局面哈希 ＋ 线字快照，不传 4,664 B 的 `Board`；运行时探测不到设备就是 CPU 参考实现。
3. **单次思考内的波前：不做。** 理由就是 §2.4.1 的四行，写进本文件，避免下一轮再被提一次。

#### 2.4.3 O6｜GPU 批量后端（训练侧 / 复盘侧可选）

- 接口同上；**唯一的消费者是 `WavefrontBatch` 与 §3.2 S2 的开局筛选**；
- **盈亏平衡点**：设一批 B 个根、每个根 CPU 成本 c（VCF 单根约 30–200 µs，**未测**），GPU 往返 L（5–20 µs 量级，未实测）。GPU 只有在 `B × c / GPU吞吐 > B × c / CPU吞吐 + L` 时才赚，即 **B 必须大到让 L 被摊薄**。按 c = 100 µs 与 L = 20 µs 估，B ≥ 200 才有意义；B ≥ 4096 才值得写 kernel（预估，未测）；
- **杀线**：刺探在 B = 256 / 1024 / 4096 三档下仍跑不过 CPU 的 `WavefrontBatch` → 整项作废、代码回收（先例：威胁延伸、LMR、futility 三轮都是这样回收的）。本机有 AMD RX 6600 XT，但 **WSL 下只有 `/dev/dxg`、没有 ROCm**，所以 WSL 里的 O6 仍然「等价不存在」；真机刺探必须在**原生 Linux ＋ Vulkan compute** 上做（§2.1 更正块）。未做真机刺探之前，本项**只允许存在「探测不到 → 走 CPU」这一条路径**进树。

### 2.5 G5 的口径建议（本版唯一请用户拍数字的地方）

把 v1.0 `:126` 的「单线程 ≥ 1M nps」拆成两格：

| 新口径 | 值 | 性质 |
| --- | --- | --- |
| G5a 单线程 | ≥ 45 万 nps（刺探后再定最终数） | O1 + O2 + O3 全过线时可望；未测 |
| G5b 整机训练吞吐 | ≥ 1M nps 合计 | 由 §4 的进程模型兑现，可测 |

理由：4.4 倍里，评估族清零只值 3.23 倍（§1.2），节点侧全开也只值 1.34–2.03 倍且已证明要牺牲 17 个必胜 think。坚持原数会让后续每一轮都拿一个不可能达标的数字写整改方案——这正是轮次140 到轮次141 已经发生过一次的事。

> **新增一条口径纪律**：O5 的证明入库**不算** nps 提升，它算「同一把思考里的节点数下降」。两者不许混着报——nps 是内核速度，节点数是搜索质量，混报会让下一轮无法判断到底是哪一侧动了。

### 2.6 `:124` 的默认值：ponder 该不该出厂就开（本版替文档补的那笔定价）

`:124` 那一格现在是「带开关达标」：`--ponder 25` 读到 30.75 %、`--ponder 50` 读到 45.80 %，但**出厂默认是 0**（`src/main.cpp:14`、`src/server/server.h:94`），理由是「它吃 CPU」。文档从没为这笔 CPU 定价，尤其是用户指出的那一项：**每个等待中的会话会多一条引擎线程**。本节把它算完，再给默认值。

#### 2.6.1 成本形状（三项实测 ＋ 一项折算）

| 项 | 值 | 性质 |
| --- | --- | --- |
| 预搜预算区间 | 下限 4,000 节点、上限 **200,000 节点**（`game_manager.cpp:53-60`，`ponder_node_budget`） | 实测（代码） |
| 折算墙钟上限 | 200,000 ÷ 228,000 nps ≈ **0.88 s 单核** | 折算（用 §1.1 的 nps） |
| 线程起 ＋ join | 28.92 µs（≈ 6.6 个节点） | 实测（轮次141） |
| 每会话预搜内存 | **+64..96 kB RSS** | 实测（轮次141） |
| 新增置换表 | **无**——`ponder_search` 是 `SearchEngine` 的成员，用的是会话自己那张表 | 实测（代码） |

**关键结论一：预搜是「节点帽」不是「墙钟」，所以它的代价有硬上界。** 它不会在人类思考的 10–60 s 里一直烧核，最多烧到 200,000 节点 ≈ 0.88 s 就自己停（`stopped == "nodes"`，轮次141 的用例 `:9076` 钉的就是这个）。用户担心的「多一条线程」因此不是一条常驻线程，而是**每次等待最多 0.88 s 的一段突发**。

#### 2.6.2 三档的净账（花掉 vs 省下）

轮次141 的「空闲节点和」与「省下 ÷ 花掉」两列，可以反推总节点是净省还是净亏：

| 预算 | 花掉（节点和） | 省下（节点和） | 省 ÷ 花 | 本手降幅中位 | 总节点净变化 |
| --- | --- | --- | --- | --- | --- |
| 0 %（＝今天） | 0 | — | — | 8.76 %（TT 自身复用，不是 ponder 的功劳） | 基准 |
| **25 %** | 850,693 | 1,082,932 | **1.273**（实测） | 30.75 % | **≈ −4 %（折算）** |
| 50 % | 1,387,226 | 1,566,178 | 1.129（实测） | 45.80 % | ≈ −3 %（折算） |
| 100 % | 1,820,303 | 1,787,538 | 0.982（实测） | 53.06 % | ≈ +1 %（折算，已转负） |

- 「省下」＝「省 ÷ 花」×「花掉」，两列都是实测，乘出来的积是折算；
- 「总节点净变化」的分母按 19–20 臂 × 30 万节点估（折算），只用来判断**符号**，不当精确值用；
- **关键结论二：ponder 在总节点上是「近乎免费」的（−3 ~ −4 %），只有 100 % 那档才转负。** 所以「它吃 CPU」这句理由只在 100 % 档成立；25 %/50 % 档真正付出的是**并发与热量**，不是节点。

#### 2.6.3 并发成本：用户指出的那一项，确实没被定过价

| 场景 | 代价 | 判 |
| --- | --- | --- |
| 单会话等待 | ≤ 0.88 s × 1 核／每次等待，+96 kB | 可接受（人类本来在闲置那条核） |
| N 个会话同时等待 | ≤ 0.88 s × N 核的突发，N ≤ 12 才不超卖 | **必须加闸**，否则是 N 倍的同一笔账 |
| 训练 quota > 0（§4.4 只留 2 核） | 与 worker 抢预留核，玩家那手的 p99 直接劣化 | **不许 ponder** |

**新增机制 P-1（ponder 槽）**：

- 全局 `ponder_slots_`，默认 **1**：拿不到槽就**不 arm**（不排队、不发帧、不重试），下一手再说；
- 训练 `train_quota > 0` 时槽数置 **0**（与 §4.4 的让位规则同一口径，避免两套优先级打架）；
- 槽在 `cancel_ponder()` 的 join 之后释放（含 `make_move` / `undo` / `request_hint` / `halt_search` 四条异常路径，`game_manager.cpp:220/277/387/475`）；
- **验收仪器**：12 个并发会话同时等待，`ponder_arms()` 的并发峰值必须 ≤ 1；且每会话 think 的 p99 与单会话档差 ≤ 5 %。这条仪器是 P-1 唯一的存在理由——没有它，槽就是个摆设。

#### 2.6.4 默认值：建议抬到 25 %，不抬到 50 %

**一句话：抬到 25 %，并且只有拿到 P-1 那个槽、且训练已停时才 arm；50 % 保留为单会话手动选项，不做默认。**

四条理由，前两条是实测，后两条是口径：

1. **25 % 是效率峰值**：省 ÷ 花 = 1.273（50 % 是 1.129，100 % 已跌破 1）。同样花一个节点，25 % 档买到的最多。
2. **25 % 的总节点降幅最大**（≈ −4 %，50 % 只有 ≈ −3 %）。50 % 多买的那 15 个百分点「本手降幅」，是用几乎等量的额外节点换来的——本手降幅更大，总账反而更小。
3. **45.80 % 那个数是自对弈口径，不能直接搬到人类对局**：轮次141 的 24 臂里「对手」是同一个引擎，它预测的应手**真的会被走出来**；人类经常走别的，命中率未测。按 45.80 % 给默认值定价，等于按最好情况定价。
4. **`:124` 只要 ≥ 25 %**：25 % 预算读到 30.75 %，是「用最小代价达标」；默认值不该为超出验收线 20 个点的余量付双倍突发。

**这次抬默认值是一次行为变更，必须按变更处理**（不能悄悄改一个数字）：

- `--ponder 0` 保留，且语义明确为「与轮次141 之前逐字节相同」，它是这次变更的对照臂；
- 验收：同一会话连想四轮 × 三副局面 × 两色（轮次141 的 24 臂），报「本手降幅中位」与「每手 p50 / p99」两组数；24 臂的着法与分值必须一个不变（轮次141 已证 20/20 同）；
- **杀线**：若人类对局（人真的在走）的实测命中率让总节点转为净增（即 省 ÷ 花 < 1），默认值回 0，ponder 只留手动开关——**这条杀线的读数今天不存在，所以默认值可以抬，但不能宣称「更快」**。

## 3. 问题二：棋力——「谁先手谁赢」的根因与六条修法

### 3.1 先分清：这是退化，还是深搜把真相暴露了

README `:213` 与轮次129 的实测（深度 4 / 400 ms，同一套系数走镜像对局，前 48 条 4 手开局里 **45 条是一方吃掉全部对局**）说明：

- 在这个强度上，**四手的局面通常已经是必胜局**；
- 搜索越深（d6 / 2 s 远深于 d4 / 400 ms），越多开局被算成「先手必胜」，「颜色通吃」的比例只会**上升**；
- 于是验证赛分数被钉在 0.5，门槛 0.56 形同虚设；`--fitness-games 2` 只有一对，适配度信号只有 0 / 0.25 / 0.5 / 0.75 / 1 五档（轮次128 实测），优化器看到的是一个平台；
- 轮次126 还量到 `--max-nodes` 把每手搜浅之后（d 分布 `{3,4}` → `{2,3}`），同 seed 的验证赛结论会翻面（0.875 晋升 ↔ 0.375 不晋升）——这是「强度与信号互相踩」的实例。

**所以问题不是「引擎变弱了」，而是「训练闭环在深度 6 上再也学不到东西」。** 加深搜索解决不了它，只会更快地把信号抹平。

### 3.2 四条修法（按建议落地顺序）

#### S1｜开局规则参数化：把「交换」变成引擎的一个选项

- 形态：`--opening-rule none|swap|soosyrv`，默认 `none` 保持现状。
  - `swap`（swap2）：黑下第 1、3 手，白在第 2 手后决定是否交换颜色；
  - `soosyrv`（Soosõrv-8 简化）：黑第 1 手天元、白第 2 手、黑第 3 手，白再决定是否交换。
- 为什么是它：先手优势是这个游戏的**规则级**事实，标准解法是规则级补偿，不是搜索级补偿。轮次129 已用实测证明「不换颜色、只换局面」不够（45/48）。
- 落地成本：这是对局流程改动，不是搜索改动；`game_manager` 要暴露交换回合，训练器读同一规则，两者口径必须一致（否则网页上换了规则、训练器不认）。
- **验收仪器**：同一套系数下，`swap` 规则跑 48 条开局，报「一方通吃比例」与「颜色决定的对局占比」两个读数，对照组是当前 `none` 规则的同 seed 结果。
- **杀线**：若交换规则下仍有 > 60 % 开局一方通吃，说明该强度下这些开局本身就是必胜局，换规则不解决问题 → 转 S2；若交换让「适配度赛钉在 0.5 的比例」不降反升（轮次129 读到过 32.5 % → 38.8 % 的反向移动），记为反向证据，权重下调而不是硬上。

#### S2｜开局集按双方胜机筛选（GPU 可插拔的位置）

- 现状：开局来自固定 8 条一组，按「轮次 + 对序」轮换（`--match-opening-plies`，缺省 0）；缺省关的原因正是开局太一面倒。
- 改什么：开场前先让引擎对每条候选开局做一次「黑白各自下的胜机评估」（各跑若干次短局，读成五手数与终局分差），只保留**双方都有胜机**的开局进训练集。筛选是批量且独立的工作，正是 §2.4.2 那个 `WavefrontBatch` / `BatchEvaluator` 的形状——这是 GPU 在本版里唯一「形状对」的位置。
- 筛选结果落盘复用（`data/training/openings.json`），不在线筛。
- **验收仪器**：筛选前后各报一遍「一方通吃比例」；筛后集合应把它压到 1/3 以下才有资格当训练集，否则说明筛选判据选错了，换判据而不是放宽阈值。
- **杀线**：筛选成本（每条开局 K 次短局）若超过省下的训练局数 → 降低 K 并复用落盘结果；若两者都救不回来 → 本项作废，训练赛退回「固定 8 条轮换」。

#### S3｜训练信号从二值胜负换成连续量

- 现状：适配度 = 胜负对；`--fitness-games 2` 时只有五档，SPRT 在一对上最大 |LLR| 2.395 < 界 2.944（轮次128：序贯检验在 1 对上根本碰不到任何界）。
- 改什么：给适配度加连续分量，**全部从现有产物里取，不加新基础设施**：
  1. 终局静态分差（`evaluate_board` 在终局点的两色分差，归一化）；
  2. 先成五一方用了多少手（`game_record` 已有逐手记录）；
  3. 认输时 probing 的深度差。
- 分量权重是**可训练参数**，不是硬编码；同时给开关，关掉时行为与今天逐字节一致。
- **验收仪器**：报两件事——`--fitness-games 2` 下适配度取值档数（从五档涨成连续分布）；同 seed 两轮的选择一致性（不许翻面）。
- **杀线**：若连续分量让同 seed 的验证赛结论翻面（轮次126 的先例），优先保结论稳定性：分量权重下调，直到翻面消失；下调到 0 仍翻面 → 本项作废。

#### S4｜深搜蒸馏样本：把深搜的着法当教材，而不是只数输赢

- 现状：`data_collector` 已在产 JSONL 样本，但样本只覆盖 alphabeta 决策的 ply——`min_search_depth_ = 1`（`data_collector.h:74`，`trainer.cpp:207` 从未改写过）把所有 vcf/must_block 的 ply 丢掉了；轮次125 实测 14/28/62 → 112/224/496 条样本，差的就是这几类 ply。
- 改什么：训练信号从「这一局的胜负」改为「这一手与一次更贵的参考搜索给出的着法差多少」。d6 的搜索直接当 d4 的老师，**深搜的优势第一次变成训练动力，而不是把对局抹平**。
- 形态：`min_search_depth_` 提升 ＋ 每样本加一份 `teacher_move`（由一次更贵/定深更大的参考搜索产生，与实际执行的那一手分开记，不许互相污染）；训练目标是一个就地可算的距离量。
- **验收仪器**：报「样本数」与「teacher 与实际一致的比例」随轮次的变化；一致率上升 = 队伍在学；同时确认样本覆盖 vcf/must_block 的 ply（断言的正是今天缺的那部分）。
- **杀线**：教师搜索贵 k 倍；若每轮对局数塌到 1/4 以下，就只对 `--fitness-games` 的对局做蒸馏，其余对局不蒸馏（半覆盖比全不覆盖强）。

### 3.3 S5｜把「胜率」换成「解题率」：本版新增的唯一不饱和标尺

**这是本版最重要的一条，它同时回答「棋力怎么进一步提升」和「怎么知道提升了」。**

上面四条修法都在解决「信号」，但都没解决一个更根本的问题：**在 d6 这个强度上，胜率作为标尺已经坏了**。轮次129 的 45/48 不是「引擎太强」，是「标尺饱和」——当两个候选系数都强到能把同一个开局算成必胜时，它们的胜率永远是 1.0 与 0.0，与系数好坏无关。

**解法：用 §6 的战术题库当标尺。** 题库里的每一道题都有唯一正确答案和难度标签，度量的是「给定节点预算，当前引擎能不能找到那一步」：

| 指标 | 定义 | 为什么它不饱和 |
| --- | --- | --- |
| `solve_rate@B` | 预算 B 个节点内找到题库正解的比例 | 题目按难度分层，弱引擎只解得出简单层；**不会出现 0 % 或 100 %**（题库构造时就按当前引擎的能力做了分层筛选） |
| `solve_rate@B` 按层 | 每层各自的解题率 | 一眼看出「涨的是哪一层」，胜率做不到这件事 |
| `first_ply_hit` | 第一层根着法里就有正解的比例 | 与节点数解耦，纯排序质量 |

- **与胜率的关系**：胜率回答「谁赢」，解题率回答「会不会」。前者被先手优势污染，后者不会——题库里每题都标了行棋方，黑白分开统计（这正是 §3.4 需要的读数）。
- **验收仪器**：同一套系数，在题库上跑 `solve_rate@{2k, 8k, 32k}` 三档，报三档与分层；一次引擎改动若让三档里任何一档掉超过 2 个百分点，判退化（比 8 局验证赛的方差小得多）。
- **成本（预估）**：40 题的快速集，`40 × 8,000 / 228,000 nps ≈ 1.4 s`；200 题的完整集 ≈ 7 s。可以进门禁（作为独立 `tools/tactics_bench.sh`，不进 `ctest`，因为 `ctest` 已有 486 s）。
- **杀线**：若题库在**当前树**上的 `solve_rate@8k` 落在 0–5 % 或 95–100 %，说明分层失败（太难以致全错 / 太易以致全对），该层作废重造，不许拿它当门禁。

### 3.4 S6｜黑白分离的系数与平衡闭环（回答「黑白要区分开」）

用户要求「根据胜率自动调整后续迭代的威胁系数，且黑白要区分开」。这句话在架构上要拆成两个独立的东西，混在一起会做出一个**看似平衡、实则变弱**的引擎：

| 诉求 | 它真正想解决的问题 | 正确的机制 |
| --- | --- | --- |
| 黑白分开调系数 | 先手优势让白方的局面天然更差，一套系数不可能同时对两边最优 | **按色系数集**（`CoefficientPair`）＋ 平衡控制器 |
| 按胜率自动调 | 人手调参慢，且人看不出「哪一侧偏了」 | 每轮读一次按色胜率，走**有界的单步修正** |

#### 3.4.1 数据结构：`CoefficientPair`

```cpp
// src/training/params.h
struct CoefficientPair {
    ThreatCoefficients black;
    ThreatCoefficients white;
    // 旧文件（单份系数）读进来时两边同值 —— 与今天逐字节一致。
    static CoefficientPair shared(const ThreatCoefficients& c);
    // 只允许这些字段在两侧不同：位置/贴边/宽度/防守权重。
    // 威胁阶梯（five..four_three）两侧必须同阶，理由见 3.4.2。
    void sanitize();
};
```

**不变量（必须有用例钉住）**：

1. `evaluate_board(board, my_color)` 的值 = 从 BLACK 视角算 `score(black stones, pair.black) - score(white stones, pair.white)`，再按 `my_color` 取号。这样 `eval(W) == -eval(B)` 这条既有不变量**按构造成立**（今天它在 `evaluator.cpp` 的注释里被写明，测试也在钉）。
2. `pair.black == pair.white` 时，整棵树的着法、分值、节点数与今天**逐字节相同**（等价性臂）。
3. 威胁阶梯同阶：`|black.live_three - white.live_three| / max(...) ≤ 20 %`，其余阶梯项同理；越界由 `sanitize()` 拉回并记一条日志（不许静默截断）。

#### 3.4.2 为什么威胁阶梯不许两侧不同

如果允许白方的 `live_three` 是黑方的 10 倍，那么这个引擎在「白方」这个角色上就是另一个引擎，**Elo 失去意义**：它赢下的每一局都可能是靠「换了个价值函数」而不是靠「更会下棋」。位置项、贴边惩罚、候选宽度、防守权重这几项不同则是有意义的——它们编码的是「站在这个角色上，哪些资源更稀缺」，这是先手优势的真实形状。

#### 3.4.3 平衡控制器（`BalanceController`）

- **输入**：上一轮验证赛的**按色胜率**（`GameRecord.winner` 与 `black_profile` / `white_profile` 已经能算，无需新数据）；
- **判据**：`wr_black` 与 `wr_white` 各自的 95 % 区间（Wilson）与 0.5 比较；只有区间不含 0.5 才算「偏了」，避免把 8 局的噪声当成信号（这条是 S3 杀线的直接后果）；
- **动作**：只改**落后那一侧**的 `position_weight_scale` / `edge_penalty` / `cand_width_*` 中的一个，步长 `step = ±10 %`，**每轮最多一步**；威胁阶梯不动（§3.4.2）；
- **上限**：累计 `K = 5` 步；到上限仍在偏 → 停手，把问题交给 S1（规则级补偿），并在报告里写明「系数补偿到头了」；
- **回滚**：任何一步之后若 §3.3 的 `solve_rate@8k` 掉超过 2 个百分点 → 回滚该步并冻结本机制；
- **杀线**：三步之内按色胜率差没有缩小，或 `solve_rate` 掉了 → 判「按色补偿无效」，回到对称系数（`pair.black == pair.white`），本项作废。

> **一句话纪律**：**按色系数是「让训练赛不一边倒」的手段，不是「让引擎更强」的手段。** 强度只认 §3.3 的解题率与整树赛 Elo，不认按色胜率——后者被这套机制本身改变了。

### 3.5 一条纪律：深度、时钟、节点三个预算口径不许混着读

轮次140 起「深度 6 / 2 s」就有两套口径（分层口径 96.4 %、全臂口径 84.4 %），而 `--max-nodes` 又会把每手搜得更浅。本版要求：

- 每篇训练报告必须同时写「目标深度 / 实际完成深度分布 / 时钟 / 节点帽」，四个数缺一不可；
- 换强度 = 四个数一起换，不许只换一个然后跨口径比较；
- 「深度 6 胜率」这类读数必须标出是定深、挂钟还是定节点口径；
- 交换规则（S1）下的读数另标规则名，与 `none` 的读数不可直接对比；
- **按色系数（S6）下的胜率读数另标「系数是否对称」**，与对称系数的读数不可直接对比。

## 4. 问题三：自我训练——进程模型、资源治理、网页控制面与一键训练

### 4.1 进程模型（supervisor ＋ workers）

```
                    ┌────────────────────────────────────────────────┐
   web/app.js ─WS──▶│ gomoku_server（唯一对外面孔，自己不训练）       │
                    │  ├── GameManager    人类对局 / 求招 / 摆棋      │
                    │  ├── ParamRegistry  参数单一真源（范围/默认/白话）│
                    │  ├── TrainBridge    UDS 客户端 + 文件 spool 读写 │
                    │  └── 控制面帧：train_* / config_* / preview_*   │
                    └───────────────┬────────────────────────────────┘
                                    │ 文件 spool（data/training/<run>/…）
                                    │ ＋ UDS（与 broker 一条，与 worker 各一条）
                    ┌───────────────▼────────────────────────────────┐
                    │ gomoku_broker（supervisor 进程，独立可执行）   │
                    │  配额：workers = 物理核 − reserved_cores       │
                    │  派活：把 (开局, 参数版本, 节点帽) 写成任务文件 │
                    │  收账：tail 各 worker 的 JSONL，汇总状态帧     │
                    │  看门：worker 退出码非 0 → 重排任务、记档       │
                    │  平衡：每轮末跑一次 BalanceController（§3.4.3）│
                    └───┬──────────────┬──────────────┬─────────────┘
                        ▼              ▼              ▼
                 gomoku_worker #1 … #N（各自一个进程）
                 每进程 sched_setaffinity 绑 1 个物理核
                         1 个 SearchEngine + 1 张 TT + 1 张 ProofTable
                         追加写 records / samples（带 run_id + seq）
```

新增两个可执行入口：`gomoku_broker` 与 `gomoku_train --worker <root>`（worker 模式复用现有 trainer，不复制一份训练逻辑）。

### 4.2 为什么是进程而不是线程（四条理由，三条有实测）

| 理由 | 依据 |
| --- | --- |
| **崩溃隔离**：worker 断言 / OOM 只死一个任务，不杀伤训练 | 本仓库的 `assert` 在 memcheck 下会 abort（轮次124 / 141 实测两类 rc=134）；线程模式下一个 assert 带走整个 trainer |
| **`--threads` 的语义已经是糊涂账** | 轮次125 实测：不带数据采集时 `--threads` 是**惰性的**（user 56.50 vs wall 57.06，三份 RSS 只差 212 kB），因为这个 flag 的含意只是「并行数据采集 worker」；进程模型把资源契约写成显式的「N 个 worker 进程」 |
| **玩家的思考必须与训练抢不到同一个物理核** | 绑核是进程级（`sched_setaffinity`）；线程绑核在同一地址空间里和搜索线程互相干扰，且本机只有 6 物理核，必须留核给 asio |
| **TT 本来就是每引擎一张** | 轮次127 量到共享表 20,448 → 21,496 kB 平坦（每 worker +71 kB），进程边界与共享表边界天然对齐，没有「多线程共享大表」把分片锁复杂度溢出的问题 |

**可移植性（必须写进设计，否则 Windows 开发机上无法验收）**：

- 主路径：POSIX（`fork`/`exec` ＋ `sched_setaffinity` ＋ UDS ＋ `flock` 的追加写）。本仓库开发环境是 WSL（README 明文），验收也按 WSL。
- Windows 回退：`CreateProcess` ＋ Job Object 看门；绑核用 `SetProcessAffinityMask`。
- 两者都不可用 → 退回当前**线程模式**，并显式上报「本机为线程模式」，行为与今天逐字节一致。
- **杀线**：若进程模型的启动 / 看门 / 收账必须在两侧各写一份、而其中一份没有仪器覆盖 → 退化为「POSIX-only ＋ Windows 保持线程」，不允许「两边都有但一边没测」的状态进树。

### 4.3 IPC：文件 spool ＋ UDS，不新增 TCP 端口

- 本机实测记录：一次并发压测曾把临时端口池打满、导致机器硬重启（`docs/PROMPT_STRESS_TEST.md`）；`docs/2026-10-19-stress-report.md` 量到 TIME_WAIT 峰值 5011 = 熔断线 8000 的 63 %、端口池 28231 的 17.7 %。**所以新 IPC 不许再开 TCP 监听。**
- 选型：
  - 大流量（对局记录、样本、逐手统计、**题库**）→ 追加写文件，每行自带 `run_id` / `seq`；broker 只读自己 tail 过的偏移，永不 seek；
  - 控制（起停、心跳、参数版本切换）→ 每 worker 一条 UDS 连接，消息是单行 JSON；
  - 崩溃安全：worker 的半行写由 broker 识别后丢弃（行不完整 / `seq` 断号），**重排任务而不是续行**——续一行被截断的 JSON 是数据污染，不是健壮性。
- **验收仪器**：worker 在写记录中途被 `SIGKILL`，broker 的任务账与文件账要在 N 秒内重新对齐；UDS 断开要在心跳超时内被发现（默认 5 s）。

### 4.4 CPU 治理：玩家的核优先，训练的核让位

- 配额公式：`workers = max(1, physical_cores − reserved_cores)`，`reserved_cores` 默认 2（1 给 asio / GameManager，1 给玩家那手正在跑的搜索）。
- 玩家一开始思考（`start_ai_thinking` / `request_hint` / ponder 起臂），broker 把**部分** worker 置 `PAUSED`（不是杀），玩家那手结束再 `RESUME`。暂停粒度是任务不是进程，断点文件保证不丢轮次。
- 绑核分配：worker 只拿 `reserved_cores … physical_cores−1`，永远不碰 0 / 1。玩家的搜索线程本来在系统调度里，但**它现在不会和任何训练 worker 挤同一个物理核**。
- 面板上一个「训练并发」滑杆：0..N；0 = 全停，N = 吃满。滑杆只改 quota，不需要重启 broker。
- **验收仪器**：三档（全训 / 半训 / 边下边训）报「一次人类 think 的 p50 / p99 墙钟」与「每秒训练节点数」。边下边训档的 p99 相对全停档劣化应 ≤ 20 %；超过说明绑核没生效（不是机器不够，这个区分很重要）。

### 4.5 网页控制面：同一个页面，两种模式

#### 4.5.1 模式是什么

「普通人机模式」＝ 今天已有的棋盘 / 落子 / 求招 / 回放；「管理自我训练模式」＝ 同一页面上的一个侧栏面板（不是第二个网页、不是第二个端口）。切换是**视图切换 ＋ 资源切换**两件事：

1. 视图：面板显隐，棋盘不被替换——切模式不会让你正在下的那局棋消失；
2. 资源：进入对局 / 思考时训练降档（§4.4），面板实时显示「已让出 N 个 worker」。

> §6 的复盘面板是**第三个视图**，但它不占第三种「模式」：它是人机模式里「这局下完了」之后的一个动作，与训练面板共用同一套 `config_*` 帧。

#### 4.5.2 帧族（沿用「只增字段、不改含义」的约定）

| 方向 | 帧 | 说明 |
| --- | --- | --- |
| C→S | `train_subscribe` / `train_unsubscribe` | 订阅 / 退订训练状态推送 |
| C→S | `train_start` `train_pause` `train_resume` `train_stop` `train_set_quota` | 控制；`train_start` 可带一组参数覆盖（可空） |
| C→S | `train_autopilot` | **一键训练**：`{profile, budget_minutes, allow_balance_step}`，服务端按 §4.8 的状态机自走 |
| C→S | `config_schema` | 拉参数清单（§5） |
| C→S | `config_set` | 改一个参数；带 `preview` 布尔 |
| C→S | `config_preview` | **预览效果**：跑一次固定针臂，不回填参数 |
| C→S | `analyze_request` | **复盘**：`{game_id 或 moves[], depth, budget}`（§6.9） |
| S→C | `train_status` | 周期推送：round、phase、worker 数、各 worker 心跳、nps、累计节点、当前最优适配度、上一条 gate 读数、**按色胜率** |
| S→C | `config_schema` | 参数清单（前端不硬编码） |
| S→C | `analyze_progress` / `analyze_result` | 复盘进度（第几手 / 共几手）与结果（§6.6 的题卡） |
| C↔S | `config_ack` / `config_reject` | 改参结果；`config_reject` 点名越界参数（沿用轮次74 / 86 的哨兵风格） |

#### 4.5.3 「所有模式开始时，所有参数都可以随时修改」

- 每次开新对局、每次起训练、每次开复盘面板，前端都先发 `config_schema` 拿一份当前真值再渲染表单，**不缓存默认值**（缓存过期 = 用户看到昨天的默认值，这是这类面板最常见的坑）。
- 参数分三类，面板用不同视觉标出：
  - `live`：立即生效（时钟、深度上限、ponder 百分比、训练并发、认输阈值…）；
  - `next_think`：下一手 / 下一轮生效（TT 槽位、候选宽度、位置项权重…）；
  - `restart`：要重开进程（TT 槽位数、设备选择、绑定目录…），面板直接禁用并写「改这项要重启服务」。
- 每次 `config_set` 都回一帧 `config_ack`，带「这句改动实际改变了什么」的一句话（例：`max_nodes: 0 → 20000，训练每手的节点帽改为定死 2 万，墙钟只剩兜底`）。

#### 4.5.4 「有大白话介绍、范围与默认值」

见 §5 参数清册。那不只是文档，它是 `ParamRegistry` 的代码内容，`config_schema` 帧原样下发。

#### 4.5.5 「可以预览效果」

- `config_preview` 在服务端跑**固定针臂**（本仓库已有这套局面：quiet / scattered × 两色 ＋ pos24），回填一组小读数：完成深度、节点数、墙钟、nps、着法与分值。**新增一格：题库 `solve_rate@8k`**——这是唯一能把「这组参数棋力更高」说清楚的预览读数。
- 预览与提交**分离**：预览不改任何状态；用户点「应用」才 `config_set`。
- 预览上限默认 3 s，且**玩家正在思考时直接拒绝**（`config_reject`，理由写明），避免预览偷走玩家那手的时钟。
- **验收仪器**：同一组参数预览两次读数一致；预览前后不改参数时，正式 think 的读数与预览同形（允许时间项抖动）。

### 4.6 参数单一真源

今天参数散在三处：`src/training/params.h`（可训练系数）、`src/main.cpp`（启动旗标）、`web/app.js` 的 `set_config`（只下发 `timeout_ms` / `max_depth`）。本版要求：

- 新增 `src/server/param_schema.h`：每条参数一条 `ParamSpec{ key, group, type, min, max, default, step, unit, when_live, desc_plain, effect_note, suggest }`；
- `ParamRegistry` 是它的单例；训练器与服务器共用同一份定义（训练器读同一文件），避免「网页能设 20、命令行只认 16」的两处口径；
- 前端零硬编码：`config_schema` 给什么就渲染什么，`min` / `max` / `default` / `suggest` 由服务端给的值裁剪输入框；
- 服务端对每个 `config_set` 做范围校验（轮次74 / 86 的既有防线），越界即 `config_reject`，不截断、不静默改。

### 4.7 验收仪器与门禁（本版新增的回归保障）

1. **训练吞吐标尺**：broker 起 1 / 2 / 4 worker（本机 6 物理核 → 4 worker ＋ 2 reserved），报每秒节点数与每轮墙钟；对比单进程同 seed 轮次。判据：每 worker 的 nps 不低于单进程的 90 %（绑核生效、没有互相踩 cache）。
2. **让位标尺**：§4.4 的三档 think p50 / p99。
3. **IPC 崩溃标尺**：`SIGKILL` 一臂 ＋ 半行写一臂，broker 账要对齐。
4. **参数面回归**：`tests/test_server.cpp` 增 `config_schema` 形状、越界拒绝、`live` / `next_think` / `restart` 三类生效时机各一例；`tests/web_frontend_check.js` 增「前端不含默认参数硬编码」一例。
5. **既有门禁不动**：`ctest 8/8`、`readme_anchor_check` 120 citations / 0 problems、WebSocket 压测约束按 `docs/STRESS_TEST_RULES.md` 不与 TSan / memcheck 重叠；TSan 对新 IPC 与新并发臂跑干净树 ＋ 5 条变异臂（变异臂必须能响——轮次141 的 M4 那 8 条 race 就是这套仪器的通电证明）。
6. **题库门禁（本版新增）**：`tools/tactics_bench.sh` 的 `solve_rate@8k` 相对上一 tag 掉 > 2 个百分点即红（§3.3）。它取代不了 `ctest`，但它是**唯一能发现「节点数变少但棋变笨」的那道门**。

### 4.8 一键训练：一个五相状态机（回答「一键训练 ＋ 按胜率自动调」）

用户要的「一键」，本质是**把六个本来要人手串起来的动作串成一个可中断、可恢复、可解释的循环**。状态机在 broker 里，不在前端（前端关掉浏览器不能停训练）。

| 相 | 做什么 | 出口条件 | 失败时 |
| --- | --- | --- | --- |
| `PREPARE` | 读 checkpoint、生成 / 复用开局集（S2）、起 N 个 worker、绑核 | 开局集就绪 ＋ worker 心跳齐 | 缺开局集 → 现场筛（`WavefrontBatch`）；筛失败 → 退回固定 8 条并记档 |
| `COLLECT` | `data_games` 局自对弈，产 records ＋ samples（S4 的 `teacher_move` 在这一相补） | 达到局数或节点预算 | 单 worker 死 → 重排该任务，不重跑整相 |
| `OPTIMIZE` | 遗传 / 爬山在适配度上搜（S3 的连续分量在此生效） | 达到代数 / 停滞代数 | 适配度全等（信号饱和）→ 记一条「饱和」并跳到 `BALANCE` |
| `VERIFY` | 候选 vs 冠军，SPRT ＋ 按色胜率 ＋ **题库解题率** | SPRT 出界或局数到顶 | 解题率掉 > 2 点 → 拒绝晋升（即使胜率好看） |
| `BALANCE` | `BalanceController` 走一步（§3.4.3），或什么都不做 | 一步走完 | 见 §3.4.3 的杀线 |

- **可中断**：`train_pause` 在相边界生效（不打断一手棋）；`train_stop` 写 checkpoint 后退出，`train_start` 从 checkpoint 续。
- **可解释**：每相结束发一帧 `train_status`，带「这一相花了多久、产出了什么、下一步为什么是它」。这是「一键」不变成「黑箱」的唯一办法。
- **一键的边界**：`train_autopilot` 只自动做**上面五相**，不做「改代码」「换算法」「调机器」。任何需要人拍板的事（比如 §8 的六件）它只报告，不代替。
- **验收仪器**：同一 seed 跑两次 `train_autopilot`，两次的相序列、每相出口条件、最终 checkpoint 的系数逐字节相同（除时间字段）。这条比任何胜率读数都硬——它证明「一键」是确定性的，不是碰运气。

## 6. 问题四：复盘分析与战术题库（特征提升）

### 6.1 目标与产出物

用户要的四件事，其实是**一条流水线的四个出口**：

| 用户的话 | 流水线里的位置 | 产出 |
| --- | --- | --- |
| 自动剔除对局前期的无意义棋子 | 第一段的过滤器（§6.4） | 一份「有信息量的手」清单 |
| 快速定位哪一步是妙手或俗手 | 第二段的判定（§6.3） | 每手一张题卡，带判定与证据 |
| 把这些棋盘加入训练库 | 第三段的导出（§6.7 a） | `teacher_move` 样本，与 S4 同一条管道 |
| 训练时可直接摆棋测试能否找到这一步 | 第四段的消费（§6.7 b） | `solve_rate@B`，**这是 §3.3 的标尺** |

**关键设计判断**：这四件事**不需要新的搜索算法**。`GameRecord` 已经逐手记了 `score` / `depth` / `nodes` / `method` / `stopped` / `partial_depth`（`game_record.h:25-41`），所以「哪一步出了事」在第一段**一次搜索都不用**就能筛出来；真正需要搜索的只有「被筛出来的那几手」，而那时用定预算（不是定时钟）复核，读数才可比。

### 6.2 两段式漏斗（＋ 一段难度标定）

```
GameRecord (JSONL, 已有)
   │
   ├─ 段 A：零搜索筛查 ─────────────────────────────── 成本 ≈ 0
   │   逐手读 score/method/depth/stopped，算摆幅与状态迁移
   │   输出：候选手集合（通常 5–12 手/局）
   │
   ├─ 段 B：定预算复核 ─────────────────────────────── 成本 ≈ 0.6 s/局（预估）
   │   只对候选手：从「落子前」的局面重新定预算搜索
   │   需要新能力：root_scores（根着法逐个分值，见 6.3.1）
   │   输出：判定 + 证据（正解、次优、分差、将杀距离）
   │
   └─ 段 C：难度标定（只对入选题卡）────────────────── 成本 ≈ 1 s/张（预估）
       节点预算几何阶梯 {1k,2k,…,256k} 二分，找「最小能解出的预算」
       输出：difficulty.solve_budget（这就是「这题有多难」）
```

三段之间是**逐段收窄**的：A 段 60 手 → 5–12 手；B 段 5–12 手 → 1–4 张卡；C 段只跑这 1–4 张。这就是「快速」的来源——不是算法快，是**不必要的工作根本不做**。

#### 6.2.1 段 A 已落地（2026-10-21，Linux 主机实测）

落点与 §6.10 一致：`src/training/replay_analyzer.{h,cpp}` ＋ `tools/analyze_main.cpp` ＋ `gomoku_analyze` 目标 ＋ 7 条用例。第一个真实读数（4 局 / 86 手，`--depth 4 --timeout-ms 400`，`--data-games 4`）：

| 量 | 实测 | 文档原预估 |
| --- | --- | --- |
| 筛出率 | **14.0 %**（12 / 86） | 「通常 5–12 手/局」→ 实测 **3 手/局**，偏低 |
| 每局候选 | 2.5（两局 5 手、两局 0 手） | — |
| `flat_game` | **2 / 4 = 50 %** | §6.4 只要求「记一条计数」，实测这条计数直接过半 |
| `replay` 手占比 | **46 / 86 = 53 %** | 文档没预料到 |
| 判定分布 | big_swing 8 / method_shift 2 / mate_cross 2 / noise 6 / opening 8 | — |

**结论一（数据源才是瓶颈）**：一半的 ply 是 `replay`——`RetryExplorer` 回退后重放的开局前缀，不是引擎的决定。这批记录里只有 match 局（game 0/2）是整局真搜的，data 局几乎全是重试续跑。**所以段 A 的产出量由「对局来源」决定，不是由阈值决定**；§6.8 的「60 手/局」假设在这个数据源上不成立（实测 21–22 手）。

**结论二（五条判据被真实数据改了五处）**：见 §6.3.3。这五处都不是设计时想到的，是跑第一份记录跑出来的——这正是 §7 把 J 排在 F 之前的那条理由。


### 6.3 判定表（四把尺）

#### 6.3.1 需要的新能力：`root_scores`

今天 `SearchResult` 只给一个 `best_move` 与一个 `score`，判定「这一步是不是俗手」需要知道**这一步在当时排第几、差多少**。所以新增：

```cpp
// src/search/search_limits.h（只增字段）
struct RootScoreEntry { Move move; int score; };
struct SearchStats {
    // ...
    std::vector<RootScoreEntry> root_scores;  // 按 score 降序，长度 = min(root_moves_done, K)
};
```

- 只在根层收集，`K` 默认 8（`analyze_max_candidates` 管的是报告长度，不是这个）；
- 不进 WebSocket 帧（帧只发判定结果，不发整张表），避免把一次思考的载荷从几百字节抬到几 KB；
- 它同时是 §4.5.5 预览的「着法与分值」那一格的正式来源。

**落地时补的一个字段（2026-10-21，第一份真实数据逼出来的）**：根表里排在后面的着法带的是**界，不是精确分**——根层给后续着法的窗口下界是「当前最好」，一次失败低返回的界往往正好等于 alpha。于是第一版段 B 拿表里的分数直接做差，12 手全是 `loss 0 / gap 0`，看着像「引擎与自己完全一致」，其实是**根本没算**。因此：

- `RootMoveScore` 增加 `bool exact`（`score > alpha_before` 才算精确）；
- `SearchEngine::exact_root_score()` 走 ponder 那条窄路（无书、无战术层、无时钟、只有节点帽），对**需要精确值的少数几手**各付一次复算；
- 段 B 只精确化两手：最好的与走的那手（`loss` 只用到它们）；`gap` 只在**有精确值**的着法里找次优，**没有证据就不宣称妙手**。


#### 6.3.2 四把尺与六种判定

记 `i` 为手序，`score_i` 为第 i 手引擎给的分（**行棋方视角**），`swing_i = (-score_{i+1}) - score_i`（正 = 走完这手后自己的形势变好）。

| 判定 | 判据（全部为可配阈值，见 §5.3） | 证据字段 | 训练价值 |
| --- | --- | --- | --- |
| **俗手** `blunder` | 定预算复核：`best.score - played.score >= analyze_swing` | 正解、实际手、差值、两者的 PV 首段 | 高（负样本） |
| **妙手** `brilliant` | `played == best.move` 且 `best.score - second.score >= analyze_gap` 且 **不是**唯一应手 且 难度 ≥ `normal` | 正解、次优手与分差、难度 | 高（正样本，且带难度） |
| **唯一应手** `forced` | 合法应手里「不输」的只有 1 个 | 该唯一手、其余手的失分 | 中（`must_block` 的题面化） |
| **反例** `counterexample` | 引擎当时给的 `score_i >= +20000`，但复核（更深/更大预算）判 `<= -90000` 或 VCF 证明败 | 两套读数并列、证明路径 | **最高**（引擎自己骗了自己） |
| **漏杀** `missed_mate` | 复核发现该局面存在 VCF/VCT 胜，而记录里 `method != vcf/vct` | 杀法主变 | 最高 |
| **无意义** `noise` | `best.score - second.score < 500` 且 `|swing_i| < 500` | — | 零（直接剔除，§6.4） |

> 「妙手」的定义里那条「不是唯一应手」很关键：一个只有一步能走的局面里走对了，叫**被迫正确**，不叫妙手。把它算进妙手会让题库塞满 `must_block`，`solve_rate` 立刻饱和（这正是 §3.3 杀线要防的形状）。

#### 6.3.3 判据的优先级：具体压过泛化（第一份真实数据改出来的五条）

设计时写的是「一条判定链」，实现后跑第一份记录（§6.2.1），五处立刻不对。记在这里，因为每一条都是**只有真数据才会暴露**的：

| # | 现象（实测） | 修法 |
| --- | --- | --- |
| 1 | 记录里有 `vcf` 8 手、`must_block` 4 手，报告却是 `method_shift 0 / must_block_run 0`——战术手同时带着巨大摆幅，全被 `BIG_SWING` 抢走标签 | **具体判据排在量级判据之前**：`must_block_run > method_shift > mate_cross > big_swing > depth_dip`。标签不是装饰，§6.3.2 给每种判定的训练价值不同，下游按 kind 加权 |
| 2 | 出现 `swing = -199000` | 那是**饱和分的假差值**（100000 → 99000）。`BIG_SWING` 现在要求**两侧都不在将杀带内**才响 |
| 3 | `depth_dip` 落在 `vcf` 手上 | 战术手的 `depth = 0` 是结构性的（它们根本不进 `alphabeta`），不是「引擎不确定」。深度判据只对非战术手生效 |
| 4 | 一手 `replay`（重放的开局前缀）被标成 `method_shift` | 新增剔除类 `REPLAYED`：`replay` / `book` 不含决策，摆幅再大也不是候选。这份样本里 86 手有 46 手属于这一类 |
| 5 | 战术层接管的那一手被判成 `NOISE`（两侧都在将杀带内 → 摆幅 0 → 「没信息」） | `NOISE` 增加一个条件：**下一手不是战术手**。摆幅为 0 不等于没信息——「vcf 从这里开始」本身就是信息 |

**一句话纪律**：段 A 的判定链不是「分数大小排序」，是「**最具体的解释优先**」。任何一条新判据进链，都要先回答「它和已有判据同时命中时，谁更能解释这一手」。


### 6.4 「自动剔除前期无意义棋子」的严格定义

用户的原话是「剔除对局前期的无意义棋子」。这句话有两个可判据的读法，本版两个都做，并且**优先用第二个**：

1. **绝对位置**：`ply < analyze_opening_plies`（默认 6）。这是用户直觉的形状，但它会误伤——第 4 手就可能已经有唯一应手。
2. **信息量**（推荐）：`gap < 500` 且 `|swing| < 500` 且 `method ∉ {must_block, forced, vcf, vct, greedy_five}`。也就是**「这步走哪都一样，且走完什么都没变」**。这个判据与手序无关：开局第 3 手若真是唯一应手，它不会被剔除；中盘第 30 手若一步平淡无奇，它会被剔除。

- 两条判据是 **OR**：命中任一条即不入候选集。
- **杀线**：若按判据 2 剔除后，一局剩下的候选手少于 2 手（说明整局都很平）→ 该局不产题卡，但要记一条 `flat_game` 计数（这个计数本身有用：`flat_game` 占比上升说明训练对局变得没内容了）。

### 6.5 难度标定：这道题有多难

对每张入选卡，用**节点预算的几何阶梯**问同一个问题：「当前引擎最少花多少节点能找到正解？」

```
budgets = {1k, 2k, 4k, 8k, 16k, 32k, 64k, 128k, 256k}
从最小开始跑；第一个命中的预算 = difficulty.solve_budget
命中即停（所以期望只跑 3–5 档，不是 9 档）
```

- 预算固定、时钟不参与（轮次121 B5 量到 `time_limit_ms = 0` 不是确定性配置，`search_engine.cpp:256-260` 会把 `remaining_time` 兜到 100 ms；所以这里必须显式 `set_max_nodes` ＋ 一个不 binding 的时限）；
- **难度分层**（写进卡片的 `layer`）：`solve_budget <= 8k` → `easy`；`8k < x <= 64k` → `normal`；`> 64k` 或解不出 → `hard`；
- **杀线**：若某层在**生成它的那棵树上**的 `solve_rate` 就是 100 %（生成器自己能秒解）→ 该层无区分度，降级为 `easy` 或丢弃。**题库不能由「已经会做的题」组成。**

### 6.6 数据格式与目录

一行一卡，追加写（与 `records.jsonl` / `samples.jsonl` 同一纪律）：

```json
{"schema":"tactics/1","id":"run_x-g0042-p17","layer":"normal","kind":"brilliant",
 "side":"white","ply":17,
 "stones":[[7,7,"b"],[7,8,"w"],[8,8,"b"],[6,6,"w"]],
 "last_move":[6,6],
 "answer":[8,9],"alt_answers":[],
 "evidence":{"best_score":3100,"played_score":3100,"second_move":[5,5],
             "second_score":-1100,"gap":4200,"loss":0,
             "budget":20000,"depth":8,"method":"alphabeta"},
 "difficulty":{"solve_budget":16000,"failed_at":8000},
 "coeffs_sha":"a3f1…","generator":"analyze/1",
 "source":{"game":"run_x/records.jsonl#42","winner":"black","reason":"five"}}
```

四个字段值得单独说明：

| 字段 | 为什么必须有 |
| --- | --- |
| `stones` 全量棋谱（不是哈希） | 卡片必须**自包含**：能直接摆到棋盘上（§6.7 b），能进 `position_setup`，能在没有原始对局文件时独立复现 |
| `coeffs_sha` | **正解依赖评估系数**。换一套系数，同一局面的「正解」可能变。没有这个字段，题库会在系数换代后静默变成一份错的答案 |
| `generator` | 生成器版本；判据改了就换版本号，旧卡不会被新尺子误读 |
| `difficulty.failed_at` | 难度是**区间**不是点：`(failed_at, solve_budget]`。只记一个数会让「8k 与 16k 之间」这种差别消失 |

目录：

```
data/tactics/
  proven/<layer>.jsonl      # 杀棋题：由 VCF/VCT 证明，与系数无关（门禁只用这一层）
  judged/<layer>.jsonl      # 判断题：妙手/俗手/反例，与系数相关（训练与展示用）
  index.json                # 各层数量、生成时间、coeffs_sha、generator 版本
```

**`proven` 与 `judged` 分开是这张表最重要的一条设计**：杀棋题的正解由「能不能成五」决定，与系数无关，所以它跨系数换代**依然有效**，可以当门禁；判断题的正解由系数决定，换代即失效，只能当训练信号。把两者混在一张表里，门禁就会在每次调参后无意义地变红。

### 6.7 三个消费方

#### a) 训练样本（与 S4 同一条管道）

- 每张 `judged` 卡产一条 `TrainingSample`，`teacher_move = answer`，`weight` 按 `kind` 加权（`counterexample` / `missed_mate` 最高，`brilliant` 次之，`forced` 最低）；
- **不新增格式**：`data_collector.h` 的 `TrainingSample` 只加两个字段 `teacher_move` / `teacher_source`（后者标 `distill` 或 `replay`），旧样本读回来两者皆空 = 没有老师，行为与今天一致；
- **杀线**：若加入题库样本后 §3.3 的 `solve_rate@8k` 不升（同 seed 对照），说明「复盘找到的题」不比 S4 的蒸馏样本强 → 题卡只留作展示，不进训练（半覆盖比全不覆盖强，但**没用的覆盖不如不覆盖**）。

#### b) 摆棋测试（`solve_rate` 的来源）

- CLI：`gomoku_analyze --bench data/tactics/proven --budget 8000 --report`；
- 网页：复盘面板上「把这道题摆到棋盘」→ 复用已有摆棋模式（`position_setup.cpp` ＋ `web/app.js` 的 setup 视图），把 `stones` 摆上去，`side` 设为行棋方，然后按 `tactics_budget` 跑一次思考，当场显示「找到 / 没找到 / 花了几千节点」；
- **这是用户那句「可直接摆棋测试当前棋力能否找到这一步」的完整落点**，它用的是已有能力，不新建棋盘。

#### c) 回归门禁

- `tools/tactics_bench.sh`：对 `proven` 层跑 `solve_rate@{4k,8k,32k}`，与上一 tag 的读数比；
- 判据：任一档掉 > 2 个百分点 → 红；
- **它不进 `ctest`**（`ctest` 已 486 s，再塞一个 7 s 的臂会让人开始跳过 `ctest`），而是作为 `build.sh` 之后的独立一步，与 `readme_anchor_check` / `web_frontend_check` 并列。

### 6.8 成本账与杀线

| 段 | 每局成本 | 性质 |
| --- | --- | --- |
| A 零搜索筛查 | **微秒级（已落地，实测 4 局 / 86 手瞬时返回）** | 实测（`gomoku_analyze`，2026-10-21） |
| B 定预算复核 | `7.2 手 × 20,000 / 228,000 nps ≈ 0.63 s` | **预估**（按 12 % 手被筛出，未测） |
| C 难度标定 | `3 张 × 4 档 × 平均 30,000 / 228,000 ≈ 1.6 s` | **预估**（按每局 3 张卡） |
| 合计 | ≈ 2.2 s/局单线程；1000 局 ≈ 37 min；4 worker ≈ 9 min | **预估** |
| 摆棋门禁 | `40 题 × 8,000 / 228,000 ≈ 1.4 s` | **预估** |

> **段 A 落地后要修的两处预估**（实测见 §6.2.1）：① 「一局 60 手」不成立，实测记录 21–22 手；② 「12 % 的手被筛出」偏高，实测 14.0 % 但**其中一半的局是 flat**（0 候选），所以 B 段的真实成本更接近「每个非 flat 局 5 手 × 定预算」。这两个数都等段 B 落地时重算，**不许拿预估当读数写进报告**。

**段 B / C 已落地（2026-10-21，同一份 4 局记录）**，三处读数与一条新约束：

| 复核强度 | 判定分布 | 产卡 | 墙钟 |
| --- | --- | --- | --- |
| `--budget 20000 --depth 6` | `none 12` | **0** | 秒级 |
| `--budget 200000 --depth 8` | `blunder 2 / missed_mate 2 / none 8` | **4** | 21.8 s（12 手） |

- **新约束（写进本节，因为它决定整条流水线有没有产出）**：**复核者必须比被复核者强。** 同一套系数、只把预算从 2 万抬到 20 万，产出从 0 张卡变成 4 张。原因是自对弈记录里的每一手都是「当时的引擎自己选的」——复核者若与它同强，结论必然是「走对了」；只有复核者更强，才看得见当时的错。所以 §6.9 的默认不是「用同一套参数复盘」，而是「**用比那一局更强的预算复盘**」，并且记录里必须带那一局用了什么强度（§3.5 的三口径纪律在这里也适用）。
- 摆棋测试（§6.7 b）在同一批卡上：`solve_rate@8000 = 0/4`、`solve_rate@200000 = 4/4`，与段 C 标出的区间（32k–64k 与 `hard`）自洽；两条 0 %/100 % 的读数都正确触发了 §3.3 的「分层失败」告警——**告警是给预算选的，不是给题选的**。


**杀线**（四条，缺一条就会做出一个「报告很好看但没用」的功能）：

1. A 段筛出率 > 40 % → 阈值太松（一局一半的手都「出事」不可能），抬高 `analyze_swing` 默认值，否则报告没人看；
2. B 段复核后「判为妙手/俗手/反例」的比例 < 10 % → 漏斗第一段在筛噪声，收紧阈值，**并且不许进 C 段**（省钱）；
3. `proven` 层在当前树上 `solve_rate` 全 0 或全 1 → 分层失败，该层作废重造（同 §3.3 杀线）；
4. 加入题库样本后 `solve_rate` 不升 → 题卡只留展示，不进训练（见 §6.7 a）。

### 6.9 网页呈现

复盘面板是**人机模式里的一个动作**，不是第三个模式：

1. 一局结束后，`analyze_request` 发出去，`analyze_progress` 每完成一手推一次（「第 23 / 60 手」）；
2. 结果回来以后，在**已有的胜率曲线**（`web/app.js` 的 `drawEvalGraph`）上打标记：红色圆点 = 俗手，绿色星 = 妙手，灰色竖线 = 唯一应手，紫色方块 = 反例；
3. 点标记跳到那一手（复用 `showReplayMove`），棋盘上高亮「实际走的」与「正解」两格；
4. 每张卡下面一行大白话：「第 17 手，白棋这步把优势从 +3.1 掉到 −0.4；当时排第 5，最好的是 H8（差 4200 分）」；
5. 「摆棋测试」按钮：把这张卡摆到棋盘上，按 `tactics_budget` 跑一次，当场给「找到 / 没找到」；
6. 「加入题库」按钮：写一行到 `data/tactics/judged/…`（要人点，不自动——自动加会把噪声一起收进去）。

## 7. 实施路线

阶段按「能不能独立回滚」切，不按「写起来顺不顺」切。每一阶段都带自己的仪器与杀线；**没有仪器的阶段不开工**。

| 阶段 | 内容 | 依赖 | 验收 | 风险 |
| --- | --- | --- | --- | --- |
| **E（口径与文档）** | G5 拆 G5a / G5b；G1 分母定义写清；「深度 / 时钟 / 节点」三口径纪律写进训练报告模板；**「nps 与节点数不许混报」**（§2.5 末） | 无 | 文档 ＋ anchor 引用修正 | 无代码风险 |

**建议的实际顺序**（本机 6 物理核、单人开发）：

```
E → J（段 A/B 先跑通，因为它是唯一不需要动引擎的）→ F（四个读数）
  → G（S3 → S1 → S4）→ H → I → K → L
```

理由：J 的第一段**零搜索**，可以立刻验证「记录里到底有多少信息」，而这个读数会反过来决定 §3.3 的标尺是否可行。先做 J 的 A 段，等于先确认「棋力尺」这个前提成立，再决定要不要为它花 F/G/H 的钱。

**回归保障（v1.0 `:554-:557` 四条继续有效，本版各补一条）**：

1. 选点一致性基准 → 把 pos24 与两副 d8 臂搬进树内常驻表；
2. 棋力回归 → 整树赛（384 局起）放在 G 阶段之后跑一次；**另加 §3.3 的 `solve_rate@{4k,8k,32k}`**，两者都要过；
3. 差分测试 → O1 / O2 必须交 42 棋盘 × 225 × 4 × 2 的那张表；A5 位置项欠的那张表一并补；**S6 的 `CoefficientPair` 必须交「两侧同值时逐字节相同」的等价性臂**；
4. 时间语义测试 → 不变；新增「预览不改状态」「`live` / `next_think` / `restart` 三类生效时机」「复盘不改对局状态」各一例。

## 9. 需要用户拍板的八件事

1. **G5 口径**：是否接受「单线程 ≥ 45 万 ＋ 整机 ≥ 100 万」替代原来的「单线程 ≥ 100 万」？若坚持原数，请同时授权一次内核重写——§1.2 的算术说明小改拿不到。
2. **O1 / O2 / O3 / O5 的先刺探再落树**：是否授权这四项树外刺探（一两天，不碰生产代码）？其中 O5 最便宜，建议单独先做。
3. **S3 连续适配信号**：是否授权把胜负之外的信号接进适配度（会改变训练行为，需一次同 seed 对照）？
4. **S1 交换规则**：是否要把它做成引擎的正式规则选项（对局流程改动）？
5. **进程模型**：是否授权 broker / worker 的进程化改造（含 Windows 回退策略）？
6. **GPU**：是否保留 `BatchEvaluator` 这个可选后端？**本机是 AMD RX 6600 XT**：WSL 下只能走 CPU（无 ROCm），原生 Linux 下首选 Vulkan compute（RADV），HIP 是未支持路径（gfx1032 不在官方列表）。**波前扩展的裁决见 §2.4：单根不做，跨根做（先 CPU）。**
7. **S6 按色系数**：是否授权 `CoefficientPair` ＋ 平衡控制器？**默认关**，打开会改变训练赛语义；且强度读数从此只认题库。
8. **J 阶段先开工**：复盘与题库不依赖任何其他阶段，是否同意把它排在 F 之前先跑通「段 A」？（它产出的第一个读数会决定 §3.3 的标尺是否成立。）
9. **`--ponder` 默认值**：是否同意从 0 抬到 **25 %**（并加 P-1 的 ponder 槽、训练期间置 0）？50 % 只作手动选项。见 §2.6.4——这是本版唯一一处**会改变出厂行为**的建议，`--ponder 0` 保留为对照臂。
