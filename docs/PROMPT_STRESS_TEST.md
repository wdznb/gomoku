```text
# 任务

 gomoku 项目的 Boost.Beast WebSocket 服务端（默认端口 8080）编写压测程序并运行，
产出一份可复现的压测报告。**这是在本机（开发机）上跑，不是专用压测机**，所以下面的硬性约束
优先于任何压测目标：宁可少测一档，也不许把机器压死。

# 背景（先读懂再动手）

gomoku 项目，qoder启动了多个 agent 各自起压测，总压力相加且互不知情。
这台机器上周被压测搞挂过一次：多个 agent 各自压测，WebSocket 连接churn 把
Windows 的临时端口打光（Tcpip 4266 / 4227），随后是无退避重连风暴，最终 CPU/DPC 饱和、
鼠标键盘无响应，只能断电重启。

所以本次压测的第一目标是**证明服务端能力边界**，第二目标才是**拿到数字**，且全程不得让端口池、内存、CPU 进入危险区。

# 硬性约束（违反任意一条即视为任务失败，立即停止并报告）

S1. **单任务独占**。同一时刻只允许一个压测任务运行。禁止并行派发多个 agent 各自起压测进程，
    禁止在后台同时保留多个 load generator。如果你是多 agent 协作，压测必须由**一个** agent
    独占执行，其余 agent 只读报告、不碰网络。

S2. **并发必须声明并封顶**。动手前先把「档位表」写进计划并等我确认：默认 50 / 100 / 200 / 400，
    每档保持 60 秒，档间爬坡 30 秒。任何情况下不得超过 500 并发。要突破必须先问我。

S3. **禁止无界"连上就断"**。容量压测的连接必须**保持**（长连接压消息吞吐）。如果确实要测握手路径，
    单独成一个用例，且建连速率 ≤ 100 次/秒、持续 ≤ 60 秒。

S4. **失败必须退避**。任何建连失败都要走指数退避：base 200ms，每次 ×2，上限 30s，叠加 ±20% 抖动。
    **绝对禁止零延迟重连**。连续失败 20 次直接退出该档并报告。

S5. **必须熔断**。客户端每 5 秒自检一次，命中任一条件立即停止加压、dump 现场、清理进程：
      - 建连失败率 > 5%
      - 本机 TIME_WAIT > 8000
      - p99 建连耗时 > 5s
      - 客户端进程 RSS 超过 2GB

S6. **单次任务总时长 ≤ 15 分钟**（含爬坡与清理）。超过就停，改天再跑。

S7. **客户端必须是异步模型**。单个 io_context + N 个线程（N = 物理核数，最多 8）驱动所有连接。
    **禁止 thread-per-client**——一万连接一万线程会把系统的 vmmem 顶到上限。

S8. **内存必须有界**。每条连接预分配固定大小的读缓冲（建议 16KB）并设上限，禁止按消息长度
    无限增长。客户端总数 × 缓冲大小必须能算出来并写进报告。

S9. **不得修改系统配置**。不要动 netsh/ sysctl。需要改就停下来告诉我，
    由我决定。

S10. **不得留下孤儿进程**。任务结束（正常或异常）都必须杀掉整个进程树，并确认端口已释放。
     用 trap / RAII 保证，不要靠"应该会退出"。

# 开跑前必须自检（把结果贴给我，再等我放行）

1. `ulimit -n` —— 必须 ≥ 2 × 最大并发，否则先说明再降档。
2. `cat /proc/sys/net/ipv4/ip_local_port_range` —— 记录临时端口范围。
3. `cat /proc/sys/net/core/somaxconn` —— 记录 accept 队列上限。
4. `ss -s` 基线快照 —— 记录 TIME-WAIT / 已建立 / orphaned。
5. 确认服务端已启动并 `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/` 有响应。
6. 确认服务端进程 PID，后续用它读 `/proc/<pid>/status` 的 VmRSS 与 `/proc/<pid>/fd` 的 fd 数。

# 压测设计

分两个独立用例，不要混在一起跑：

**用例 A：容量压测（主用例）**
- 目标：并发长连接数 × 消息吞吐
- 每连接：握手成功后发 `{"type":"ping"}`，收到 `pong` 记一次往返
- 每连接每 1 秒最多发 1 条消息（不要打满，先测连接规模再测消息速率）
- 档位：50 → 100 → 200 → 400，每档 60s，档间爬坡 30s
- 每档记录：连接成功率、消息往返 p50/p95/p99、吞吐 msg/s、错误数

**用例 B：握手压测（单独、限速）**
- 目标：accept + WebSocket 握手路径的极限
- 速率 100 次/秒，持续 60s，连接建立后立刻优雅关闭（不发消息）
- 只在用例 A 全部通过、且我明确同意后才跑

# 执行流程

1. 写自检结果 + 档位计划，等我确认。
2. 先跑 **单点冒烟**：1 个连接、发 3 条消息、收 3 条 pong、正常关闭。通过才继续。
3. 按档位逐档爬坡。**每档结束打印该档指标，并暂停 10 秒观察**；任一熔断条件命中就终止全部后续档位。
4. 全部跑完后 `sleep 130` 等 TIME_WAIT 自然回收，再抓一次 `ss -s` 对比基线。
5. 清理进程树，确认 `ss -tn state time-wait | wc -l` 回落到基线附近。

# 报告必须包含

- 环境：`ulimit -n`、端口范围、服务端 PID、客户端线程数
- 每档一张表：并发 / 连接成功率 / p50 / p95 / p99 / 吞吐 / 错误数 / 客户端 RSS / 服务端 VmRSS / 服务端 fd 数
- 基线 vs 结束时的 `ss -s` 对比
- 结论：服务端在什么并发下开始劣化，劣化表现是什么（延迟、错误、内存、fd）
- 复现命令（一条能重跑的最小命令）

# 禁止事项（再强调一遍）

- 禁止多个 后台agent 同时跑压测
- 禁止零延迟重连
- 禁止 thread-per-client
- 禁止无上限并发
- 禁止改系统网络配置
- 禁止在发现异常后"再压一会儿看看"
- 禁止把压测代码混进生产代码提交；压测程序放 tests/ 或 tools/stress/ 下单独提交

# 如果中途发现机器变卡

立刻 `kill` 全部压测进程并告诉我，不要尝试"等它自己恢复"。机器卡住时你也没有机会再发指令。
```

## 这份提示词的几个设计要点

| 条款 | 针对的事故环节 |
| --- | --- |
| S1 单任务独占 | 事故直接诱因：多个 agent 各自起压测，总压力相加且互不知情 |
| S2 并发封顶 + 先确认 | 把"压多少"从执行细节提升为需要人工签字的决策 |
| S3 禁止连上就断 | 连接churn 是端口耗尽的直接来源；WebSocket 本该测长连接 |
| S4 强制退避 | 掐断「端口耗尽 → 立即重连 → 更快耗尽」的正反馈环，这是最关键的一条 |
| S5 熔断 | 给自动化加刹车，避免"发现异常后继续压" |
| S6 时长上限 | 限制爆炸半径的时间维度 |
| S7 异步客户端 | 避免 1 万线程把 vmmem 顶到 48GB 上限 |
| S9 不改系统配置 | 防止 agent 自作主张去改 netsh/注册表"解决问题" |
| S10 不留孤儿进程 | 上次事故后很可能有残留进程继续吃端口 |
