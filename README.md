# 五子棋 AI 深度思考系统

一个高性能的五子棋AI系统，具备深度思考、自我训练和参数优化能力。

### 会话落盘

```bash
./gomoku_server --sessions data/sessions        # 会话文件目录（默认值）
./gomoku_server --records data/x/records.jsonl  # 完局追加到的训练记录流
./gomoku_server --no-sessions                   # 关闭落盘：不写会话文件，对局只活在这个进程的内存里（同进程重挂仍可续，进程一停就无可恢复）
```

每局一个文件 `data/sessions/<token>.json`，内容见「会话与断线续局」。目录建不出来时服务器打印
原因并关闭落盘继续运行——端口能服务、棋能下，比一个写不进去的目录重要；写盘失败同样只报在
stdout，不会打断对局。`data/sessions/` 与 `data/training/` 都在 `.gitignore` 里。

路径类选项（`--web-dir`、`--book`、`--sessions`、`--records`、`--params`）**给空串就是启动即报错退出**
（退出码 1，错误信息点名是哪个 flag）：空路径多半是 shell 变量没展开，而不是「不要这个功能」，
关闭有专门的 `--no-book` / `--no-sessions`。把 `--book ""` 当成禁用会让人以为开局库还在，
把 `--sessions ""` 当成关闭则会让完局静默地不落盘。

## 自我训练（阶段3）

训练器 `gomoku_train` 用自我对弈评估威胁系数，每轮的流程是：

1. 用遗传算法或爬山法在系数空间中搜索一个候选参数集；
2. 让候选与当前冠军对战（每对组合执黑白各一次），得到验证分；
3. 验证分 ≥ `--accept-score`（默认 0.56）才晋升为新冠军，并写入 `--out`；
4. 生成若干盘自我对弈作为训练数据（对局记录 + 特征样本，JSONL 追加）；
5. 保存 checkpoint，中断后可 `--resume PATH`（断点文件路径）继续，续跑进度写回同一个文件。

```bash
cd build
./gomoku_train --rounds 20 --method genetic --population 8
```

常用选项（完整列表见 `--help`）：

| 选项 | 默认值 | 说明 |
| --- | --- | --- |
| `--method` | `genetic` | `genetic` 或 `hill`（爬山法） |
| `--rounds` | 3 | 训练轮数；配合 `--resume` 表示**额外**轮数 |
| `--depth` / `--timeout-ms` | 4 / 400 | 训练对局的搜索深度与单步思考预算 |
| `--max-moves` | 60 | 单盘步数上限，未分胜负记为和 |
| `--fitness-games` | 2 | 评估一个候选所用的对局数 |
| `--verification-games` | 8 | 晋升前的验证对局数 |
| `--accept-score` | 0.56 | 晋升门槛（必须 > 0.5，即仅靠“不输”不能晋升） |
| `--data-games` / `--threads` | 4 / 2 | 每轮采集数据的自我对弈盘数与并发线程 |
| `--no-data` | — | 只调参，不采集数据 |
| `--no-resign` | — | 训练对局中禁止认输（认输会截断数据） |
| `--params` | 内置默认 | 起始参数文件；**不能与 `--resume` 同时给出**，两者都声称是本轮的起点，同给时启动即报错退出（退出码 1），因为续训会把断点里的系数整套换掉，这里载入的文件根本用不上 |
| `--out` | `data/training/best_params.json` | 冠军参数输出位置 |
| `--records` / `--samples` | 空 | 对局记录 / 训练样本 JSONL |
| `--checkpoint` | `data/training/checkpoint.json` | 断点文件；与 `--resume` 同时给出时必须指向同一个文件 |
| `--resume` | — | 从断点继续训练，需要一个断点文件路径；进度写回该文件，与 `--checkpoint` 路径不同、或与 `--params` 同时给出，都是启动即报错退出（退出码 1） |

产物目录 `data/training/` 已被 `.gitignore` 忽略，训练不会污染仓库。

训练期间开局库始终关闭：比赛要衡量的是系数的差别，而开局库会把双方都引到同一着记忆着法上，把这个差别掩盖掉。

实测默认配置（`--depth 4 --timeout-ms 400 --max-moves 60`）下自我对弈是会分胜负的，但**胜负由先手颜色决定，而不是由系数决定**：轮次 50 记录的两盘都在 27 手内由黑棋成五，轮次 54 把缺口棋型与禁手判定收紧之后，四盘记录全部改为**白棋**成五——黑棋现在更容易撞上三三/四四，而白棋的空洞终于被当成威胁。因为验证赛是同一套系数互换黑白各打一局，这种“颜色通吃”会让验证分正好落在 0.5，所以门槛刻意设在 0.56：候选必须**赢下它不占颜色优势的那一局**才能晋升（这是实测现象，不是棋力结论）。副作用是 `--fitness-games 2`（只有 1 对）时优化器能看到的信号只有 0 / 0.5 / 1 三档，几乎是个平台；要更有区分度就调大 `--fitness-games`，代价是每轮对局数成倍增加。

参数文件里的整数会做**范围校验**：JSON 用 64 位存整数而 `get<int>` 只做截断，`five: 4294967396` 会被读成 `100`，因此这类文件直接拒绝而不是套用截断值；坐标同理，只有元数据（节点数、搜索深度）允许回落到默认值。

## 摆设棋局（自定义开局）

除了从空盘开始对局，还可以直接把一个自定义局面摆上桌：后端判断它是否合法（黑白手数差、
黑方禁手、是否已有五连），并据此算出下一步轮到谁（黑先手，因此手数相等是黑行棋，黑多一子是白行棋）。

### 三种输入形式

| 形式 | 字段 | 说明 |
| --- | --- | --- |
| 完整棋盘 | `board` | 15×15 嵌套数组、225 元行优先数组，或文本棋盘字符串：分隔（逗号 / 空格 / 制表符 / 分号 / 换行）或**连写的 225 字符长串**，一行或整个文件都行 |
| 位棋盘 | `bitboard` | `{"black":[4 个 uint64], "white":[4 个 uint64]}`，第 `row*15+col` 位表示该格，只允许 `< 225` 的位；字可以是十进制整数，也可以是带 `0x` 前缀的字符串（字符串避免 JSON 浮点丢掉 64 位精度） |
| 落子序列 | `moves` | `[row, col]` 或 `{"row":…,"col":…}` 的列表，按黑白交替自动着色，`first` 指定首手颜色（默认 `black`） |

三者只能出现一个，同时出现或全部缺失都会被拒绝。位棋盘与落子序列没有符号歧义，因此不需要
标志确认；棋盘形式必须说明黑/白/空对应哪些标志（见下）。

### 标志识别

`board` 里的每个符号按下面顺序尝试匹配，第一个能覆盖**全部**出现的符号的读法被采用：

| 黑 | 白 | 空 |
| --- | --- | --- |
| `1` | `2` | `0` |
| `1` | `-1` | `0` |
| `B` | `W` | `.` / `_` / `-` / `·` |
| `X` | `O` | `.` / `_` / `-` / `·` |
| `黑` | `白` | `空` / `.` / `_` / `-` / `·` |

字母大小写等价（`b`/`w`/`o` 同大写）。识别不了就**直接拒绝**并列出看到的符号，绝不猜：一套
棋盘里混用 `1/2/0` 与 `B/W/.` 会被拒，而不是把认不出的符号当成空、悄悄把棋子抹掉。
前端导入会把 `check_position` 回显的标志写在弹窗里，认错了就用旁边的 黑↔白 / 黑↔空 / 白↔空 就地改
（标志说明与棋盘一起换）；自动化训练与测试不需要这一步——模板里写明 `encoding` 即可直接载入。

### 分隔与连写

棋盘文本先按“15 行 × 15 格”解析；行数或某行格数不对时再按整盘的**连续长串**解析，两种写法
都支持，文件和报文里都一样：

- **有分隔**：225 个用逗号 / 空格 / 制表符 / 分号分开的格子，可以换行也可以挤在一行；
- **无分隔**：一整串只含黑/白/空三种符号的字符（例如 `...BW....` 连写 225 个），按字符逐个解析，
  中文标志（`黑/白/空`）同样可以连写。连写串按 UTF-8 码点切分，不会把一个汉字拆成三格。

落到长串解析时，出现**第四种**符号会先报“连续棋盘含 N 种符号 (…)”而不是格数不对——符号种类
比长度更是问题所在；`1/-1/0` 这套标志无法连写，`1-10` 之类根本分不出格，这类数据集必须带分隔符。
长度不对时报“棋盘有 N 格，需要 225 格（15x15，分隔或连写皆可）”，而行数或行内格数错的棋盘仍按
原来的“第 1 行有 3 格，需要 15 格”提示，方便定位是排版问题还是长度问题。

### 标准模板

`data/` 下的七个模板就是给训练、复盘与测试用的标准格式，都是可被后端直接识别的合法局面
（3 黑 2 白，轮到白方）：

- `position_template.json` —— 规范文档：`version` / `type` / `encoding` / `board`
- `position_template.csv` —— 逗号分隔的 0/1/2 棋盘
- `position_template.txt` —— 每格一符号的 `B`/`W`/`.` 棋盘
- `position_flat_template.txt` —— 同样 225 格连写成一行（`B`/`W`/`.`，无分隔符）
- `position_flat_template.csv` —— 一行 225 个逗号分隔的 `1`/`-1`/`0`
- `position_bitboard_template.json` —— 4×uint64 位棋盘对
- `position_moves_template.json` —— 落子坐标序列 + `first`

导出用的规范文档由 `position_to_json(board)` 产生，前端“导出”按钮写出的是同一种形状，因此
导出的文件可以原样再导入。

### 代码入口

不依赖 JSON 与网络的核心解析层是 `src/core/position_setup.h`：`parse_grid_text`、
`detect_grid_encodings`、`position_from_grid`、`position_from_bitboard`、`position_from_moves`、
`validate_position`。JSON / 文件层在 `src/server/position_json.h`：`position_from_json`、
`position_from_text`、`load_position_file`、`position_to_json`。训练与测试可直接调用它们摆出
指定局面；服务器则用 `GameManager::set_position` 把局面装上会话的棋盘。

装上之后**只摆局面、不开新局**：状态回到 `waiting`，已有的思考线程被 join 并丢弃，回放分析清空，
AI 不会自动落子。玩家随后选择执子颜色或直接落子，这局才开始（选择颜色/落子也是唯一会清除“摆棋待定”
标记的两个动作，因此空盘之外也仍能选边）。

## 使用

1. 启动服务器后，在浏览器中打开 `http://localhost:8080`
2. 选择执子颜色（黑棋先行或白棋后行）
3. 点击棋盘落子
4. AI 会自动应答

### 界面布局

页面不滚动、无标题、无进度条：**棋盘始终居中**，边缘显示坐标（列 `A–O`、行 `1–15`）；
其余空间被“棋盘四角 → 最近的页面四角”的四条连线切成上/下/左/右四块，各块的内容取
该梯形的内接矩形，因此不会被斜线裁掉：

| 分区 | 内容 |
| --- | --- |
| 上 | 状态栏：系统提示 + 轮到谁，按级别着色（绿=信息成功、琥珀=需要注意、红=拒绝/错误/断线、灰=叙述） |
| 下 | 常用按钮：执黑/执白、悔棋/求招/认输/终止/重开、深度与超时、摆棋与视角按钮；摆棋中前两组与深度/超时**就地换成**摆棋按钮与三个交换按钮，下面另起一行状态提示 |
| 左 | 回放分析：载入本局分析、⏮ ◀ 自动 ▶ ⏭ ✕、评估曲线、当前手详情 |
| 右 | 落子记录：每手坐标 + 引擎数据，点击跳转回放；摆棋中改为**摆棋记录**（标题随之切换） |

几何在 JS 里按视口计算（`layout()`），窗口尺寸变化会重排；棋盘边长取
`min(780, 宽-2×侧栏, 高-2×上下栏)`，四区互不重叠。

### 视角（旋转 / 镜像）

底栏的 **旋转**（顺时针 90°，按钮上显示当前角度）与 **镜像** 只改变**显示**：棋子、星位、
边缘坐标一起跟着变换，点击会先反算回真实坐标再发给服务器，服务器与棋谱始终使用真实坐标。
坐标标签按当前视角重新标定——旋转 90° 后上边缘是行号、左边缘是列字母，读到的两个标签仍然
合成该子的真实坐标（如 `H8`）。

### 功能按钮

- **执黑 / 执白**: 选择执子颜色（黑棋先行）
- **悔棋**: 撤销上一步（会同时撤销 AI 的回应）
- **求招**: 让 AI 给出当前最佳落子建议，结果标在棋盘上并写入状态栏；推荐算好后局面如果又落了一手，
  这一份建议作废，服务器回一条错误而不是把旧局面里的着法画到新局面上
- **认输**: 认输结束对局
- **终止**: 中断 AI 的当前思考
- **重开**: 重置棋盘开始新对局

### 回放分析

- **载入本局分析**: 取回本会话逐手的引擎数据（方法、分值、深度、节点、耗时），
  之后可用 ⏮ ◀ ▶ ⏭ 逐手回看、**自动** 连续播放（再点变 **暂停**）、**✕** 退出回放回到当前局面
- 回放中的棋盘左下角会标出“回放 · 第 N 手”；落子记录里的每一手都可以直接点击跳转
- 评估曲线按**黑棋视角**绘制：引擎的分值属于刚落子的一方，因此白棋的分值取反后入图；
  红点表示该手分值超出曲线量程（已证胜负）。曲线宽度随左栏宽度自适应
- 悔棋会使已载入的分析失效（手数与索引都对不上），需要重新载入

### AI 设置

- **超时秒**: AI 思考的最大时间（**秒**）。搜索越深需要越长的截止时间，所以这个框的取值范围由深度决定：
  最小 `深度 × 2`、最大 `深度 × 4`，改深度时自动回到该区间的最小值（默认即是），手填越界会被夹回来。
  下发服务器时换算成毫秒，服务器限制在 100–120000
- **深度**: AI 搜索的最大深度（2–20）。输入框的范围只是网页规则，服务器对 `set_config` 与
  `request_hint` 送来的 `max_depth` 一律夹到 1–20，回读到的即是夹取后的值
- 两项改动会通过 `set_config` 立即下发，对本局后续的 AI 落子生效；恢复会话时按会话保存的值回填
  （只刷新区间，不改动会话自带的截止时间）。回填是**逐键**的：会话文件里没写的那一项（`0`）沿用
  服务器当前值，不会因为一项缺席就把另一项已保存的值一起丢掉

### 摆棋

摆棋改的是**工作副本**：进入摆棋时把当前棋盘与落子记录原样抄一份，之后所有编辑都落在这份副本上，
**确认** 是唯一写服务器的一步，**取消** 直接丢掉副本（棋盘还原、落子记录不动）。

点底栏的 **摆棋** 进入，再点一次等同于取消。进入后底栏**就地换面**：被禁用的 执黑/执白 与
悔棋/求招/认输/终止/重开 两组换成 清空/导入/导出 与 确认/取消，深度/超时那一组换成 黑↔白/黑↔空/白↔空
（摆棋期间这两个输入框没有意义），最右的 摆棋/旋转/镜像 保持不变——棋盘不被任何抽屉或弹窗挡住。
顶部状态栏同时给出琥珀色提示：**点击棋盘任意位置后依次标记为 黑 / 白 / 空**，底栏下面一行显示当前计数。

- **直接在现有棋盘上摆**: 点棋盘按 空→黑→白→空 循环刷格；刷的是真实格子（旋转/镜像后点的位置仍映射回
  真实坐标），本地计数即时显示黑白手数与轮到谁，合法性（手数差、禁手、已有五连）由 **确认** 时的服务器校验兜底
- **右侧摆棋记录**: 进入摆棋时自动把当前落子记录写进摆棋记录（摆棋摆上去、落子记录里没有的那些子排在最前），
  点任意一步棋盘就切到那一步的状态，再点一次回到完整局面；编辑与导入都会同步这份记录
- **清空**: 只清空副本棋盘（摆棋记录随之清空），对局本身的落子记录不受影响
- **导入**: 弹窗（唯一会盖住棋盘的界面）。拖拽或点选局面文件（json / csv / txt 皆可）、或直接粘贴棋盘
  （分行、带分隔符、225 格连写、位棋盘、落子序列、局面 JSON），**识别** 干跑一次解析，回显
  `识别到的标志：黑=B 白=W 空=.` 与黑白手数、轮到谁；随后 **确认** 把这份读法写进副本，**取消** 什么都不改
- **交换**: 底栏的三个按钮换副本棋盘，导入弹窗里标志提示旁边的三个换**识别结果**（标志说明与棋盘一起换，
  所以下面那行读起来仍是当前读法），用于在写入副本之前修正识别错的标志；无符号的形式（位棋盘、落子序列）
  没有标志可错，弹窗里的这三个按钮会置灰。黑↔白 只改颜色、保留记录顺序，牵涉“空”的交换会改变哪些格子有子，
  因此按行序重建摆棋记录
- **导出**: 导出当前副本为规范 JSON 文档（`position.json` 下载），可原样再导入
- **确认**: 把副本作为局面摆上服务器棋盘（`set_position`），状态回到“等待选边”，AI 不会自动落子；
  底栏换回对局面、摆棋记录随即消失，落子记录仍保留，**选择执子颜色后**才清空落子记录、按新局运行
- **取消**: 退出摆棋，棋盘还原为对局当前局面，落子记录保留
- 服务器拒绝（例如 AI 正在思考、局面不合法）时留在摆棋里，改好再点 **确认** 即可重试
- **旋转 / 镜像** 是显示层变换，摆棋中同样可用，改的是视角而不是局面本身

## WebSocket 消息协议

### 客户端 → 服务器

```json
{"type": "choose_side", "color": "black"}
{"type": "make_move", "row": 7, "col": 7}
{"type": "undo"}
{"type": "request_hint", "timeout_ms": 5000, "max_depth": 8}
{"type": "request_replay"}
{"type": "set_config", "timeout_ms": 5000, "max_depth": 8}
{"type": "resign"}
{"type": "stop_thinking"}
{"type": "restart"}
{"type": "check_position", "position": {"board": [[...]], "encoding": {"black": 1, "white": 2, "empty": 0}}}
{"type": "check_position", "position": "文本棋盘或局面对象字符串", "encoding": {"black": "B", "white": "W", "empty": "."}}
{"type": "set_position", "position": {"bitboard": {"black": [0, 281474976710656, 65537, 0], "white": [0, 562954248388608, 0, 0]}}}
{"type": "resume", "token": "9af83343549460e1"}
{"type": "ping"}
```

`position` 可以是局面对象，也可以是文本（粘贴的棋盘——分行、带分隔符或 225 格连写成一串，
或整份 JSON 文档字符串）；顶层 `encoding` 会并入文档，作为调用方声明的标志映射。

`resume` 是握手后的第一件事：token 认得就接回那局（`resumed: true`）；认不得、格式不对，或记录读得
出来却重建不出棋盘的，就另开一局（`resumed: false` + 一个新 token）——那种不可读的记录文件原地保留
在磁盘上、不再被覆写，供人工查看。任何情况下都回一帧 `session`。token 只允许小写十六进制（它同时
是文件名），非法值不会碰到磁盘。

### 服务器 → 客户端

```json
{"type": "state_sync", "board": [[...]], "current_turn": "black", "game_status": "playing"}
{"type": "move_made", "row": 7, "col": 7, "color": "black"}
{"type": "ai_move", "row": 7, "col": 8, "color": "white", "score": 1234, "thinking_time_ms": 5000}
{"type": "undo_success", "move_count": 4, "game_status": "playing"}
{"type": "hint_result", "row": 8, "col": 8, "score": 1234}
{"type": "thinking_progress", "depth": 4, "nodes": 50000}
{"type": "game_over", "winner": "black", "reason": "five"}
{"type": "game_restarted", "game_status": "waiting"}
{"type": "session", "token": "9af83343549460e1", "resumed": true, "player_color": "black",
 "game_status": "playing", "current_turn": "white", "position_pending": false, "move_count": 6,
 "winner": "", "reason": "", "timeout_ms": 5000, "max_depth": 8, "board": [[...]]}
{"type": "session_taken_over", "token": "9af83343549460e1"}
{"type": "replay", "game_over": true, "winner": "white", "reason": "resign",
 "moves": [{"row": 7, "col": 7, "color": "black", "method": "human",
            "score": 0, "depth": 0, "nodes": 0, "elapsed_ms": 0}],
 "base": [{"row": 8, "col": 8, "color": "white"}]}
{"type": "error", "message": "Invalid move"}
{"type": "position_preview", "ok": true, "black_count": 3, "white_count": 2, "side_to_move": "white",
 "encoding": {"black": "1", "white": "2", "empty": "0"}, "board": [[...]]}
{"type": "position_preview", "ok": false, "error": "黑 3 子、白 0 子：黑先手，黑白差只能是 0 或 1"}
{"type": "position_set", "board": [[...]], "current_turn": "white", "game_status": "waiting",
 "position_pending": true, "black_count": 3, "white_count": 2}
{"type": "pong"}
```

`state_sync`（`choose_side` 的回应）与 `session`（`resume` 的回应、服务器开局新会话时的主动播报）
携带**服务器权威棋盘**：前端必须照它们重画棋盘并采用其中的 `current_turn`，否则页面上可能显示服务器
并没有的子。`thinking_progress` 的 `elapsed_ms` 与 `depth` 随迭代加深推进，`ai_move` 是这一次思考的
终点。

`session_taken_over` 只在同一个 token 被另一个标签页 `resume` 接管时出现：服务器把它发给被替掉的
那个连接，随后立即 `close`（见「会话与断线续局」里的后到者接管）。客户端收到后取消重连定时器、
不再自动重连（`reconnect` / `resume`），但 `localStorage` 里的 token 保留——刷新页面仍可把这局拿
回来。

`replay` 是本会话对局的逐手分析：`method` 为 `human` 表示玩家落子（无搜索数据），
其余为引擎返回路径（`book` / `vcf` / `vct` / `alphabeta` / `greedy`）；
`score` 是**刚落子一方**视角的分值，非 AlphaBeta 路径不填 `depth` / `nodes`。`base` 是摆棋摆上去、
`moves` 里没有的那些子：只有 `moves` 读不出摆棋对局的棋盘，前端重画时先铺 `base` 再按顺序落 `moves`，
轮次也按两者之和取。

`position_preview` 是干跑结果，不会改动会话状态；识别失败也用 `ok:false` + `error` 回答而不是
`error` 消息，方便表单内联显示。`encoding` 只在棋盘形式下出现（位棋盘与落子序列没有标志可言）。
`set_position` 失败才走 `error`，成功回 `position_set`，其中 `position_pending: true` 表示局面已
摆好但尚未开局：此时 `choose_side` 仍然可用，AI 不会自己落子。带 `board` 的文档必须说明 `encoding`
（文件里写好，或 `check_position` 之后由玩家确认再带上），否则会被拒绝。

`set_position` 抹掉上一局之前会先把它结算回它自己的会话文件：上一局有内容（落过子、摆过子或选过边）
时按 `重开` 同款换一个新 token——旧文件留在旧 token 名下不再被覆写，客户端从随后的 `session` 帧里
拿到新 token；只有没动过的空局才原地接着用——摆棋摆了一份**全空**的局面同样算没动过，它一颗子都没摆。摆棋开局的上一局按已有导出规则不进 `records.jsonl`，
只留在会话文件里。新局的会话文件 `created_ms` 从这一刻重新起算。

### 连接保活与重连

服务器按**双向静默**回收会话：一次读或写都会把套接字的到期点往后推到 120 秒，所以 120 秒内
毫无往来的连接（被关掉的标签页、掉线的客户端）会被清掉，而正在长考的连接不会误伤。前端每
30 秒发一个 `ping`（服务器回 `pong`，客户端忽略它）来占住这个窗口——玩家对着棋盘思考十分钟也
不会被踢。

连接断开时前端按 1、2、4、8…（上限 15 秒）退避重连，状态栏用琥珀色显示“N 秒后重连（第 k 次）”，
期间任何点击都会提示“消息未发出”而不是静默丢弃。重连成功后前端立刻拿保存的 token 发 `resume`
把原来那局接回来，见下节。

### 会话与断线续局

对局不挂在 socket 上，而是挂在**服务器会话表**里，键是一个 16 位十六进制 token：

- 握手成功不等于开局。第一条需要棋局的消息（或 `resume`）才让服务器建 `GameManager`，并回一帧
  `session{token, resumed: false, ...}`；前端把 token 存进 `localStorage`，之后刷新、掉线、甚至
  服务器重启都能凭它找回同一局。
- 连接断开只是 **detach**：停止并 join 那条正在写这个 socket 的搜索线程、清空回调、立刻落一次盘，
  棋局本身留在表里 30 分钟。期间 `resume` 回来是热挂载；超过 30 分钟则退回磁盘态（快照进 cold
  索引、引擎释放掉），再 `resume` 时按记录重建棋盘——token 依旧有效。
- 同一个 token 被第二个标签页 `resume` 时后到者接管：先给旧连接发一帧 `session_taken_over` 再关掉
  它、停下它可能正在跑的思考，再按当前局面重新武装 AI；旧标签页收到告知后不再自动重连（token 仍
  保留，刷新可取回）。
- 每 10 秒扫一遍会话表，把**内容变了**的会话原子写入 `data/sessions/<token>.json`（先写 `.tmp`
  再 rename，进程死在中途也不会留下半个文件）；一子未落的空会话不写，所以反复点“重开”不会攒出
  垃圾文件。收到退出信号时同样刷一遍，Ctrl+C 不会丢掉最后一个 10 秒。
- 文件里的 `record` 就是训练侧的 `GameRecord` JSON（同一份 schema，不做转换），因此**随时复盘、
  随时续下、也能直接拿去训练**。终局且这局本就从空盘开始，就把这一行追加进
  `data/training/records.jsonl`；摆棋开局的对局另有 `base` 棋子，从空盘读不出同一个局面，所以只
  留在会话文件里，不进训练流。
- 服务器启动时读一遍 `data/sessions/`，token 因而不受进程重启影响。读不出来的文件跳过并打印原因，
  不会让服务器起不来。

`session` 是权威状态帧：`board` 是服务器此刻的棋盘，`move_count` 是盘上子数，`player_color` 为空
表示还没有人选边，`position_pending` 表示摆好的局面尚未开局。前端在 `resumed: true` 时照它重画并
补一次 `request_replay` 取回逐手分析（回来的状态是“已恢复对局 / 已恢复摆好的局面”，且停在实时视角
而不是回放第 1 手）；在 `resumed: false` 时只保存 token、不动本地状态，免得盖掉同一批请求自己的
回应。`重开` 会把手上那局结算成文件并换一个新 token，旧文件仍然可以凭 token 找回来看。

### 阶段2：高级搜索

- ✅ VCT（连续活三胜）搜索

- ✅ 开局库
- ✅ 异步控制（AI 独立线程思考 + 多会话并发）

> 说明：搜索为**迭代加深的单线程** AlphaBeta；“多线程”指异步思考控制（每次 AI 落子起一个工作线程，
> 支持多会话并发与超时中断），并非同一着棋的并行搜索。

### 阶段3：自我训练
- ✅ 对局记录系统（3.1）
- ✅ 自我对弈 + 悔棋再战（3.2）
- ✅ 训练数据收集（3.3）
- ✅ 遗传算法优化 + 爬山法（3.4）
- ✅ Elo评分系统（3.5）
- ✅ 训练主循环与断点续训（3.6）

> 说明：训练对象是**威胁系数**，`five` 与 `forbidden_penalty` 不参与调参——前者是 AlphaBeta
> 的将杀阈值（硬编码 100000）与静态评估上限的公共基准，后者是规则而非棋力。轮内给候选算 fitness 时这两个常量一律取**冠军**的取值，比较的双方永远同一条规则。
> “悔棋再战”从最靠近终局、且还有未尝试分支的那一步重新展开，配合 D4 对称类去重，
> 使重复的镜像变化不占用探索预算。

### 阶段4：优化
- ✅ 位棋盘优化（4.1）
- ✅ 对称去重（4.2，训练侧 + 搜索侧根节点）
- ✅ 前端增强（4.3）
- ✅ 对局回放分析（4.4）

> 说明：4.1 把每条线（行/列/两族斜线）压成一个 64 位字，9 格窗口用 `(own << 9) | blocked`
> 索引一张 2^18 的形状表；表在首次使用时由既有的窗口解码器跑完全部键位生成（约 4.7ms，
> 常驻 256KB），因此形状语义与原实现按构造等价，标量解码只保留为测试对照。
> 同一颗格子的黑方窗口与白方窗口读的是同两条线（黑子即白方的堵点），所以走法排序与
> 全盘评估改为一次算完两色（`recognize_position_both`）；新增的差分测试逐字段比对单次
> 扫描与两次单色识别，全 225 格 × 两色 × 42 个棋盘一致，节点数与选点也逐条一致。
> 增量式全盘评估做过量化评估后放弃：一手棋影响 4 条线上 ±4 格共约 15 个候选格
> （12 子局面占候选集 27%），落子+撤销的代价与节点上那次全量重扫基本持平。
> 4.2 只在根节点丢弃镜像重复的候选着法：棋盘在某个 D4 变体下映射回自身时，同一轨道只保留
> 索引最小的格子；无自对称的中局（绝大多数局面）完全不受影响，选点与不含去重的根搜索一致。
> 4.4 由 `GameManager` 逐手记录引擎分析（落子与悔棋与棋盘同步），前端用
> `request_replay` 取回后驱动回放与评估曲线；4.3 顺带修好了“AI 设置”只作用于求招、
> 从未下发给搜索引擎的问题（现通过 `set_config` 下发）。
